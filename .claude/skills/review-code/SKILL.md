変更内容をレビューします。**自分では直さず、指摘と根拠を示します。**

## 1. 変更範囲の確認（最初にやる）

```
git status --porcelain
git diff --numstat
git diff --stat
```

- 変更されたファイルが承認範囲内に収まっているか
- 範囲外のファイルが含まれていないか
- 意図しない削除・移動がないか
- 承認対象外のファイル（設定・スキーマ・CI 定義など）が混ざっていないか

**範囲逸脱があれば、それを最優先の指摘にする。**

## 2. ルール適合性

`CLAUDE.md` と `.claude/rules/` に反していないか。特に確認する点：

- 指示されたファイル以外を変更していないか（`quality.md` 第 1 節）
- 既存コードの書き方に追従しているか（第 2 節）
- 未実施のテストを PASS と報告していないか（第 3 節）
- 完了の定義を満たしているか（第 5 節）
- **不要な AI 生成表記・ツール宣伝文言が入っていないか**（第 8 節）
- 法令・規約・ライセンス上必要な表示が消されていないか
- `Co-Authored-By` 等の帰属情報が改変されていないか

## 3. 設計との整合性

- 承認された設計方針どおりか
- 逸脱している場合、その箇所と理由が報告されているか

## 4. 既存コードとの一貫性

- 命名規則、ディレクトリ構成、コメントの密度
- 既存の抽象化を使っているか。独自方式を持ち込んでいないか
- 新しい依存が追加されていないか

## 5. 実装の妥当性

- エラー処理。握りつぶしていないか
- 境界条件と異常系
- 既存機能を壊していないか

## 6. 報告の裏付け

- 「テストが通った」という報告に出力の裏付けがあるか
- 未検証の項目が PASS と書かれていないか
- 実行できなかった検証が明示されているか

## 報告の形

指摘ごとに次を書く。

- 該当箇所（ファイルパスと行）
- 何が問題か
- 根拠（どのルール・どの既存実装に反するか）
- 重大度：範囲逸脱 / ルール違反 / 品質 / 軽微

最後に合否判定と理由、確認できなかった観点を書く。
**根拠なく「問題なし」と書かない。** 何を確認したかを列挙する。

## このスキルが使うツール

読み取りと差分確認のみ。修正は行わない（指摘のみ）。

**frontmatter に `allowed-tools` は書かない。**
公式仕様では `allowed-tools` は列挙したツールの**使用を許可する**フィールドであり、
制限するものではない（制限は `disallowed-tools`）。
本リポジトリは「共通配布では何も無条件許可しない（`allow` は空）」方針のため、
スキル側から権限を付与しない。
