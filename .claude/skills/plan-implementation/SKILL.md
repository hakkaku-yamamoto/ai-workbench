依頼を実装可能な計画に落とします。**計画だけで終わらせず、
承認に必要な情報が揃っているかを先に確認します。**

## 1. 承認範囲の確認（最初にやる）

タスクスコープ承認の 7 項目（`.claude/rules/approval.md` 第 7 節）が
揃っているか確認する。

1. 対象リポジトリ（`owner/repo`。1 タスク 1 リポジトリ）
2. 開発目的（完成判断に使える具体性）
3. 変更を許可する範囲（ファイル・ディレクトリ・パターン）
4. 変更禁止の対象
5. 作業ブランチ（既定ブランチは不可）
6. 許可する Git 操作（commit / push / PR 作成を**個別に**）
7. 完了条件とテスト条件

**欠けていれば計画を立てる前に人間へ確認する。**
特に第 6 項に書かれていない Git 操作は実行できない。

## 2. 現状の把握

`survey-project` スキルの結果があれば使う。無ければ、少なくとも
対象ファイルの現在の実装と既存の規約を読む。

## 3. 計画の組み立て

各ステップについて次を決める。

| 項目 | 内容 |
| :- | :- |
| やること | 具体的な作業 |
| 変更するファイル | 承認範囲内であることを確認済のもの |
| 担当役割 | architect / developer / tester / reviewer / security / uiux-designer |
| 完了条件 | 何をもって終わりとするか |
| 依存 | 先に終わっている必要があるステップ |

- 並列にできるものと順序が必要なものを分ける。
- **承認範囲を超えるステップを計画に入れない。**
  必要だと判断したら、計画に含めずに「範囲外のため要確認」として報告する。

## 4. テスト条件の明確化

- 実行するテスト・Lint・型チェックのコマンドを特定する
- 新しく書くテストの対象（正常系と異常系）
- 検証できない部分と、その理由

## 5. リスクの洗い出し

- 壊れうる既存機能
- 不可逆な操作が含まれるか（含むなら人間が実施する作業として分離）
- STOP 条件（`approval.md` 7-5）に触れうる箇所

## 報告の形

- 承認範囲の 7 項目の確認結果（欠けている項目を明示）
- 計画（ステップ、担当、変更ファイル、完了条件、依存）
- テスト条件
- リスクと未確認事項
- 範囲外として除外したもの

## このスキルが使うツール

読み取りと計画のみ。ファイルの変更は行わない。

**frontmatter に `allowed-tools` は書かない。**
公式仕様では `allowed-tools` は列挙したツールの**使用を許可する**フィールドであり、
制限するものではない（制限は `disallowed-tools`）。
本リポジトリは「共通配布では何も無条件許可しない（`allow` は空）」方針のため、
スキル側から権限を付与しない。
