テストを回し、失敗を**原因から**直して再テストします。
承認範囲内であれば、この反復に逐一の確認を求めません。

## 1. 実行するものを特定する

- 承認の第 7 項（テスト条件）に指定があればそれに従う
- 指定がなければプロジェクトの定義を調べ、**何を実行するつもりかを先に示す**
- **スクリプトの中身を読む。** `test` や `build` という名前で
  本番に影響する処理が走る可能性があるため、名前だけで判断しない

## 2. 実行して記録する

- コマンドと出力を記録する
- 失敗した件数、失敗したテスト名、エラーメッセージ
- 実行できなかったものは理由を記録する

## 3. 原因を特定する

- エラーメッセージとスタックトレースを読む
- 該当コードを読み、**なぜ失敗するか**を言葉にする
- 再現する最小の条件を特定する

**原因を特定せずに直さない。** 「とりあえず変えたら通った」は修正ではない。

## 4. 直す

- **実装側を直す。テストや期待値を書き換えて通さない。**
  テストが誤っていると判断した場合は、変更せず報告して確認を求める
- 承認された変更範囲内のファイルのみを直す
- 既存コードの書き方に合わせる
- 修正は最小限にする。関係のない整形や改善を混ぜない

## 5. 再テスト

- 同じコマンドを再実行する
- 直したテストが通り、**他のテストが壊れていないこと**を確認する
- 通るまで 3〜4 を繰り返す

## 6. 止める条件

次に該当したら反復をやめて報告する。

- 承認範囲外のファイルを直す必要がある
- 原因が特定できないまま同じ失敗が続く
- 直すには仕様の判断が必要
- テスト自体が誤っていると判断した
- 本番環境・共有環境・既存データに影響する修正が必要

## 報告の形

- 実行したコマンドと出力
- 失敗の内容と特定した原因
- 行った修正（ファイルと要点）
- **修正と再テストの回数、最終的に通ったか**
- 回避策で通した場合は、回避策であることと根本原因が未解決であること
- 未検証の範囲
