# 安全ルール（safety）

対象：このリポジトリで動作するすべてのエージェント・スキル・セッション。
位置づけ：[../../CLAUDE.md](../../CLAUDE.md) の最上位原則 2 と 5 の詳細。

---

## 1. 層の区別

操作は 3 層に分かれる。CLAUDE.md 原則 2 と同じ分類であり、両者が矛盾してはならない。

### 1-a. エージェントは実行しない（承認があっても代行しない）

以下は、人間が「やっていい」と言った場合でも**エージェントが自動で実行してはならない**。
人間自身の手で実施してもらう。

| 操作 | 理由 |
| :- | :- |
| 本番環境へのデプロイ | 影響範囲が不可逆。ロールバック手順の確認が必要 |
| 本番 DB のスキーマ変更・データ変更・マイグレーション実行 | 不可逆。バックアップ検証が前提 |
| 既存データ・バックアップ・スナップショットの削除 | 復旧不能になりうる |
| IAM / ACL / リポジトリ権限 / Ruleset の変更 | 防御層そのものを壊す |
| 課金が発生する操作（有料プラン変更、有料 API の新規契約、リソース増強） | コスト影響が人間の決定事項 |
| 本番・共有環境で有効な秘密情報の生成・登録・ローテーション | 鍵の管理責任は人間側 |
| 認証情報を使ったサインイン・アカウント作成 | 認証は人間が行う |

承認の意味は「人間が手順を実行する」であり、「エージェントが代行する」ではない。
エージェントの役割は、**手順書を出すところまで**である。

**ローカル開発専用のダミー値・テスト用のランダム文字列・`.env.example` のプレースホルダ作成は、
この層に該当しない。** これらは実在の秘密情報ではないため 1-c として扱う。
ただし生成した値を報告文・ログ・コミット内容に出力しない。

将来、承認付きで本番操作をエージェントに実行させる場合は、**別途の安全設計と明示承認が必要**である。
本ルールの緩和を単独で行わない。

### 1-b. 禁止（経路そのものを使わない）

| 操作 | 代わりに通す経路 |
| :- | :- |
| `main` への直接 push | 作業ブランチ → PR → 人間による merge |
| force push（`--force` / `-f` / `--force-with-lease` / `+refspec`） | 通常の push。履歴を書き換えない |
| PR の merge、auto-merge の有効化 | 人間が merge する |

### 1-c. 人間の個別承認を得てから実行する

| 操作 | 承認時に明示すること |
| :- | :- |
| commit | 変更内容と変更ファイルの一覧 |
| push | push 先のブランチ名 |
| PR 作成 | タイトル・本文・base ブランチ |
| 非本番環境（ローカル / dev / staging）へのデプロイ | 環境名とデプロイ先 |
| 非本番 DB の参照 | 接続先と、扱うデータの性質（後述 1-d） |
| 非本番 DB の変更 | 接続先と変更内容、戻し方 |
| タグ・リリースの作成・変更・削除 | 対象のタグ名・リリース名 |
| 依存パッケージの追加・更新・削除 | パッケージ名・バージョン・用途 |
| 外部サービス連携の追加 | 連携先と送信データ |
| 指示範囲外のファイル変更 | 変更理由と対象ファイル |
| 読み取り・診断のための調査操作 | 何を確認するためか |

承認の単位と流用禁止は [approval.md](approval.md) を参照する。

### 1-d. DB を扱うときの追加の注意

**参照操作であっても無条件に安全とは扱わない。**

- 接続先が本番、または本番のレプリカ・バックアップである場合は、参照であっても 1-a として扱う。
  エージェントは実行せず、人間に依頼する。
- 接続先が不明な場合は実行しない。STOP して接続先を確認する。
- 個人情報・機密性のある業務データを含むテーブルは、参照であっても承認時にその旨を明示する。
- 取得した行の内容を報告文・ログに貼り付けない。件数・カラム名・構造の説明に留める。
- 実データが必要な場合は、必要最小限の範囲を明示して承認を求める。
- マイグレーション・スキーマ変更系のコマンドは、接続先を問わず 1-a として扱う。

## 2. `main` の保護

- `main` への直接 push は禁止。
- `main` への force push は禁止。
- `main` の削除は禁止。
- `main` への変更は、必ず作業ブランチ → PR → **人間による merge** の経路を通す。

GitHub 側でも `protect-main` Ruleset により PR 必須・削除禁止・force push 禁止が強制されている。
ローカルのルールはそれを前提にした**二層目**であり、Ruleset の代替ではない。
詳細は [github.md](github.md) を参照する。

## 3. 破壊的なファイル操作

- 再帰削除（`rm -rf` / `rm -r` / `Remove-Item -Recurse` 等）は、承認があっても実行しない。
- ワイルドカードを伴う削除は、人間の明示承認なしに実行しない。
  対象が何件・どのファイルに展開されるかを、承認前に列挙して提示する。
- 単一ファイルの削除は、人間の個別承認を得てから実行する。
- `.git/` 配下の直接操作は禁止。
- `git reset --hard` / `git clean -f` 系による未コミット変更の破棄は、承認があっても実行しない。
- `git checkout --` / `git restore` による未コミット変更の破棄は、人間の明示承認なしに実行しない。
- ファイルを上書きする前に、**必ず対象の存在と内容を確認する。**
- 既存ファイルと同名のファイルを「新規作成」する指示を受けた場合は、上書きせず STOP する。

## 4. 秘密情報（Public リポジトリ）

**このリポジトリは Public である。** 登録した内容は取り消しても履歴・キャッシュ・インデックスに残りうる。

### 登録してはならないもの

- API キー、アクセストークン、OAuth クライアントシークレット
- パスワード、パスフレーズ、秘密鍵、証明書の秘密部分
- 本番 DB の接続情報（ホスト名・ユーザー・パスワード・接続文字列）
- 非公開の会社情報、社内固有の業務ルール、取引先名
- **社内アプリ・社内プロダクトの名称**（公開済みであると確認できないもの）
- 組織の内部構造、部署名、担当者名
- 個人情報（氏名、メールアドレス、電話番号、住所、社員番号）
- 機密性のある業務データ、実データのサンプル
- 本番環境固有の秘密設定、内部ホスト名、内部 IP、内部 URL

### 許可されるもの

- `.env.example` 等のテンプレートに置くプレースホルダ（`YOUR_API_KEY_HERE` 等）
- ローカル開発専用のダミー値・テスト用のランダム文字列
- 一般化された記述（「社内アプリ A」「対象アプリは別途決定」等）

### 守るべきこと

- 設定値は `.env.example` のような**プレースホルダのみ**を置く。実値は置かない。
- 秘密情報は環境変数または秘密情報管理サービスから読む。リポジトリに持たせない。
- ログ・エラーメッセージ・報告文に秘密情報を含めない。値そのものを出力しない。
- 会社固有の機密ルール・社内アプリ名が必要になった場合は、このリポジトリに追記せず、
  **別の Private 管理領域に分離する。**
  分離方式は [../../docs/ARCHITECTURE.md](../../docs/ARCHITECTURE.md) の「セキュリティ方針」に記載する。
- 誤って秘密情報を記録してしまった場合は、**自己判断で履歴を書き換えず** STOP して報告する。
  Public リポジトリでの漏洩は、鍵のローテーションが必要な事故であり、履歴の消去だけでは解決しない。

## 5. 技術的ガードの設計方針

`.claude/settings.json` の permission ルールは、次の方針で構成している。

| ルール種別 | 用途 | 対応する層 |
| :- | :- | :- |
| `deny` | 承認があっても実行させない。破壊的操作、本番相当の変更、権限変更、`main` への push、PR merge | 1-a / 1-b |
| `ask` | 人間の個別承認を得て実行する。読み取り・診断を含む調査操作もここに置く | 1-c |
| `allow` | 空。共有ファイルの `allow` はワークスペースの信頼（trust）承認まで適用されないため使わない | — |

**読み取り専用の操作を `deny` に入れない。**
`deny` は `allow` で例外を作れないため、`deny` に入れた操作は承認による回復手段が失われ、
各開発者が `settings.local.json` で緩和することもできなくなる。
調査・診断が必要な操作は `ask` に置き、承認で通す。

## 6. 技術的ガードの限界

permission ルールは防御の一層だが、**単独で安全性を保証しない。**
以下の限界は設計上の前提である。

### 6-1. コマンド文字列の照合だけで本番環境は識別できない

**これは最も重要な限界である。**

`vercel --prod` のような明示的なフラグは照合できるが、以下は照合できない。

- 環境名がプロファイル・環境変数・設定ファイル側にある場合
  （`AWS_PROFILE=prod aws s3 rm ...`、`kubectl --context=prod ...` の別表記、`.env` 経由の切替）
- 接続文字列・ホスト名から本番かどうかを判定する必要がある場合（DB クライアント全般）
- 同じコマンドが環境によって異なる対象を指す場合（`terraform apply` の workspace 依存）
- 組織独自の命名（`prod` でなく `live` / `main` / 顧客名 など）

したがって、**「本番は deny で止まる」と考えてはならない。**
本番環境の操作を防ぐのは、1-a の行動規範と、人間が本番の認証情報を
エージェントの実行環境に置かないことである。
`deny` パターンは「明らかな本番操作に一段の壁を置く」ための補助に過ぎない。

### 6-2. Bash の deny ルールは表記の変更で回避されうる

Claude Code の Bash ルールはコマンド文字列のパターン照合である。公式ドキュメントが挙げる例：

- `Bash(curl *)` は `curl https://example.com` に一致するが、`/usr/bin/curl https://example.com` や `sh -c 'curl https://example.com'` には**一致しない。**
- `Bash(rm *)` は `rm -rf build/` に一致するが、`/bin/rm -rf build/` や `bash -c 'rm -rf build/'` には**一致しない。**
- `Bash(git push *)` は `git push origin main` に一致するが、`git -C . push origin main` や `git -c push.default=current push` には**一致しない。**

緩和策として `Bash(/bin/*)` / `Bash(/usr/bin/*)` / `Bash(bash -c *)` / `Bash(sh -c *)` /
`Bash(git -C *)` / `Bash(git -c *)` を `ask` に置き、これらの経路に確認を入れている。
ただし網羅ではない。別のパスやラッパーを使う回避は依然として成立する。

### 6-3. 引数を制限するパターンは脆い

`Bash(curl http://example.com/ *)` のように引数で対象を絞る書き方は、URL の表記揺れで容易に外れる。
公式ドキュメントも「fragile」と明記している。

クラウド CLI の変更系 deny（`Bash(aws * delete*)` 等）は、この脆いパターンを
あえて使っている。目的は網羅的な遮断ではなく、**明らかな破壊操作に一段の壁を置くこと**である。
サブコマンドの別表記・引数順の違い・新しいサブコマンドでは外れる。

### 6-4. Read / Edit ルールの適用範囲は限定的

`Read` / `Edit` の deny ルールは、Claude Code の組み込みファイルツールと、
Claude Code が認識する一部の Bash コマンド（`cat`、`head`、`tail`、`sed`、`tee`、リダイレクト先）に適用される。
**ファイル名を引数に取らない読み取り**（カレントディレクトリでの `grep -r pattern .` など）や、
**自分でファイルを開くスクリプト**（Python / Node のコード）には適用されない。
OS レベルで全プロセスを遮断するには sandbox が必要である。

また、`Read` の deny は同じパスへの `Edit` / `Write` も遮断する。
このため `.env` 系の deny は `.env.*` の一括指定ではなく、
`.env.local` / `.env.production` 等を列挙する形にしている。
一括指定にすると `.env.example` の作成・編集まで不可能になるためである。
**列挙は網羅ではない。** 列挙にない名前（`.env.<独自名>`）は deny されない。
`.gitignore` 側は `.env.*` を一括除外しているため、コミットは防がれる。

### 6-5. 環境別ツールは別ルール

`Bash(...)` と `PowerShell(...)` は別のツールであり、ルールも別に書く必要がある。
Windows 11 で運用する場合、PowerShell 側のルールが欠けていると Bash 側の deny は意味を持たない。
本リポジトリの `settings.json` は両方を記述している。

PowerShell ルールはエイリアスが正規化されるため、`PowerShell(Remove-Item *)` は
`rm` / `del` / `rd` / `erase` / `ri` / `rmdir` も対象になる。
この性質により、`Remove-Item` を一括 deny にすると PowerShell からのファイル削除が
一切できなくなるため、本リポジトリでは再帰削除のみを deny とし、
単一ファイル削除は `ask` としている。
ただし PowerShell は引数の位置が自由なため、`-Recurse` の位置を
パターンで捉えきれない組み合わせが残る。

### 6-6. 環境ランナーは素通しになる

`npx`、`docker exec`、`devbox run`、`mise exec` などは引数をコマンドとして実行するが、
Claude Code の組み込みラッパー除去対象ではない。
`npx` / `pnpm dlx` / `bunx` / `docker` は `ask` に置いたが、内側のコマンドは
個別ルールがないと制御されない。

### 6-7. permission ルールは「指示」ではなく「設定」である

ルール文書（CLAUDE.md / `.claude/rules/`）はコンテキストとして渡される指示であり、
遵守は保証されない。公式ドキュメントも
「Claude treats them as context, not enforced configuration」と明記している。
決定論的に遮断するには Hooks（`PreToolUse` で exit code 2）が必要である。

### 6-8. したがって多層防御を前提とする

| 層 | 役割 | 本工程での状態 |
| :- | :- | :- |
| GitHub Ruleset（`protect-main`） | サーバ側強制。`main` の PR 必須・削除禁止・force push 禁止 | **設定済・Active** |
| 最小権限の認証 | トークンのスコープを必要最小限に絞る。本番の認証情報をエージェントの実行環境に置かない | 未整備（次工程） |
| permission ルール（`settings.json`） | セッション内の事故防止。善意の誤操作を止める | **設定済**（限界は 6-1〜6-7） |
| Hooks（`PreToolUse` 等） | ツール呼び出しの決定論的な遮断。exit code 2 で停止 | **未実装**（次工程の候補） |
| ルール文書（`.claude/rules/`） | エージェントの判断基準 | **設定済** |
| 人間の承認 | 最終的な責任の所在 | 常時 |

`permissions.allow` ルールと `additionalDirectories` は**ワークスペースの信頼（trust）を承認するまで適用されない**が、
`deny` と `ask` は即時適用される。本リポジトリの `settings.json` は意図的に `deny` と `ask` のみで構成している。

`bypassPermissions` モードは permission ルールを飛ばすため、`permissions.disableBypassPermissionsMode` を `"disable"` に設定して無効化している。

## 7. 判断に迷ったとき

**迷ったら実行しない。** STOP して、以下を人間に報告する。

1. 何をしようとしたか
2. なぜ迷ったか（どの情報が欠けているか）
3. 考えられる選択肢と、それぞれの影響範囲
4. 推奨案（根拠つき）

勝手に安全そうな方を選んで進めることも禁止する。選択は人間の判断事項である。
