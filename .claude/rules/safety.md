# 安全ルール（safety）

対象：このリポジトリで動作するすべてのエージェント・スキル・セッション。
位置づけ：[../../CLAUDE.md](../../CLAUDE.md) の最上位原則 2 と 5 の詳細。

---

## 1. 層の区別

操作は 3 層に分かれる。CLAUDE.md 原則 2 と同じ分類であり、両者が矛盾してはならない。

### 1-a. エージェントは実行しない（承認があっても代行しない）

以下は、人間が「やっていい」と言った場合でも**エージェントが自動で実行してはならない**。
人間自身の手で実施してもらう。

| 操作 | 理由 |
| :- | :- |
| 本番環境へのデプロイ | 影響範囲が不可逆。ロールバック手順の確認が必要 |
| 本番 DB のスキーマ変更・データ変更・マイグレーション実行 | 不可逆。バックアップ検証が前提 |
| 既存データ・バックアップ・スナップショットの削除 | 復旧不能になりうる |
| IAM / ACL / リポジトリ権限 / Ruleset の変更 | 防御層そのものを壊す |
| 課金が発生する操作（有料プラン変更、有料 API の新規契約、リソース増強） | コスト影響が人間の決定事項 |
| 本番・共有環境で有効な秘密情報の生成・登録・ローテーション | 鍵の管理責任は人間側 |
| 認証情報を使ったサインイン・アカウント作成 | 認証は人間が行う |

承認の意味は「人間が手順を実行する」であり、「エージェントが代行する」ではない。
エージェントの役割は、**手順書を出すところまで**である。

**ローカル開発専用のダミー値・テスト用のランダム文字列・`.env.example` のプレースホルダ作成は、
この層に該当しない。** これらは実在の秘密情報ではないため 1-c として扱う。
ただし生成した値を報告文・ログ・コミット内容に出力しない。

将来、承認付きで本番操作をエージェントに実行させる場合は、**別途の安全設計と明示承認が必要**である。
本ルールの緩和を単独で行わない。

### 1-b. 禁止（経路そのものを使わない）

| 操作 | 代わりに通す経路 |
| :- | :- |
| `main` への直接 push | 作業ブランチ → PR → 人間による merge |
| force push（`--force` / `-f` / `--force-with-lease` / `+refspec`） | 通常の push。履歴を書き換えない |
| PR の merge、auto-merge の有効化 | 人間が merge する |

### 1-c. 人間の個別承認を得てから実行する

| 操作 | 承認時に明示すること |
| :- | :- |
| commit | 変更内容と変更ファイルの一覧 |
| push | push 先のブランチ名 |
| PR 作成 | タイトル・本文・base ブランチ |
| 非本番環境（ローカル / dev / staging）へのデプロイ | 環境名とデプロイ先 |
| 非本番 DB の参照 | 接続先と、扱うデータの性質（後述 1-d） |
| 非本番 DB の変更 | 接続先と変更内容、戻し方 |
| タグ・リリースの作成・変更・削除 | 対象のタグ名・リリース名 |
| 依存パッケージの追加・更新・削除 | パッケージ名・バージョン・用途 |
| 外部サービス連携の追加 | 連携先と送信データ |
| 指示範囲外のファイル変更 | 変更理由と対象ファイル |
| 読み取り・診断のための調査操作 | 何を確認するためか |

承認の単位と流用禁止は [approval.md](approval.md) を参照する。

### 1-d. DB を扱うときの追加の注意

**参照操作であっても無条件に安全とは扱わない。**

- 接続先が本番、または本番のレプリカ・バックアップである場合は、参照であっても 1-a として扱う。
  エージェントは実行せず、人間に依頼する。
- 接続先が不明な場合は実行しない。STOP して接続先を確認する。
- 個人情報・機密性のある業務データを含むテーブルは、参照であっても承認時にその旨を明示する。
- 取得した行の内容を報告文・ログに貼り付けない。件数・カラム名・構造の説明に留める。
- 実データが必要な場合は、必要最小限の範囲を明示して承認を求める。
- マイグレーション・スキーマ変更系のコマンドは、接続先を問わず 1-a として扱う。

### 1-e. 非本番環境の扱い

一括承認（[approval.md](approval.md) 第 7 節）を受けている場合、
非本番環境の操作は次のように分かれる。

| 対象 | 扱い |
| :- | :- |
| ローカルでのテスト実行（単体・結合・Lint・型チェック） | **範囲内なら自動実行できる。** 何度繰り返してもよい |
| ローカルの一時ファイル・テストデータの作成と削除 | **範囲内なら自動実行できる。** 作成したものは後片付けする |
| ローカルの開発用 DB（自分の環境にしかないもの） | 範囲内なら自動実行できる。ただし 1-d の注意は適用される |
| **共有のステージング DB** | **対象環境が承認で明示されている場合に限る。** 他の人の作業に影響するため、黙って触らない |
| **非本番環境へのデプロイ**（dev / preview / staging） | **対象環境が承認で明示されている場合に限る。** 環境名が承認に書かれていなければ実行しない |
| **外部サービスへの変更**（SaaS の設定、Webhook、外部 API への書き込み） | **対象サービスが承認で明示されている場合に限る** |
| 本番環境 | 環境を問わず 1-a。承認があっても実行しない |

判断の基準：
**自分の環境だけで完結し、やり直せるもの**は範囲内で自動実行できる。
**他の人・他のシステムに影響が及ぶもの**は、その環境・サービスが
承認に明示されていなければ実行しない。

「staging だから安全」とは扱わない。共有環境は共有資源である。
環境名が承認に書かれていない場合は、推測せず STOP して確認する。

## 2. `main` の保護

- `main` への直接 push は禁止。
- `main` への force push は禁止。
- `main` の削除は禁止。
- `main` への変更は、必ず作業ブランチ → PR → **人間による merge** の経路を通す。

GitHub 側でも `protect-main` Ruleset により PR 必須・削除禁止・force push 禁止が強制されている。
ローカルのルールはそれを前提にした**二層目**であり、Ruleset の代替ではない。
詳細は [github.md](github.md) を参照する。

## 3. 破壊的なファイル操作

- 再帰削除（`rm -rf` / `rm -r` / `Remove-Item -Recurse` 等）は、承認があっても実行しない。
- ワイルドカードを伴う削除は、人間の明示承認なしに実行しない。
  対象が何件・どのファイルに展開されるかを、承認前に列挙して提示する。
- 単一ファイルの削除は、人間の個別承認を得てから実行する。
- `.git/` 配下の直接操作は禁止。
- `git reset --hard` / `git clean -f` 系による未コミット変更の破棄は、承認があっても実行しない。
- `git checkout --` / `git restore` による未コミット変更の破棄は、人間の明示承認なしに実行しない。
- ファイルを上書きする前に、**必ず対象の存在と内容を確認する。**
- 既存ファイルと同名のファイルを「新規作成」する指示を受けた場合は、上書きせず STOP する。

## 4. 秘密情報（Public リポジトリ）

**このリポジトリは Public である。** 登録した内容は取り消しても履歴・キャッシュ・インデックスに残りうる。

### 登録してはならないもの

- API キー、アクセストークン、OAuth クライアントシークレット
- パスワード、パスフレーズ、秘密鍵、証明書の秘密部分
- 本番 DB の接続情報（ホスト名・ユーザー・パスワード・接続文字列）
- 非公開の会社情報、社内固有の業務ルール、取引先名
- **社内アプリ・社内プロダクトの名称**（公開済みであると確認できないもの）
- 組織の内部構造、部署名、担当者名
- 個人情報（氏名、メールアドレス、電話番号、住所、社員番号）
- 機密性のある業務データ、実データのサンプル
- 本番環境固有の秘密設定、内部ホスト名、内部 IP、内部 URL

### 許可されるもの

- `.env.example` 等のテンプレートに置くプレースホルダ（`YOUR_API_KEY_HERE` 等）
- ローカル開発専用のダミー値・テスト用のランダム文字列
- 一般化された記述（「社内アプリ A」「対象アプリは別途決定」等）

### 守るべきこと

- 設定値は `.env.example` のような**プレースホルダのみ**を置く。実値は置かない。
- 秘密情報は環境変数または秘密情報管理サービスから読む。リポジトリに持たせない。
- ログ・エラーメッセージ・報告文に秘密情報を含めない。値そのものを出力しない。
- 会社固有の機密ルール・社内アプリ名が必要になった場合は、このリポジトリに追記せず、
  **別の Private 管理領域に分離する。**
  分離方式は [../../docs/ARCHITECTURE.md](../../docs/ARCHITECTURE.md) の「セキュリティ方針」に記載する。
- 誤って秘密情報を記録してしまった場合は、**自己判断で履歴を書き換えず** STOP して報告する。
  Public リポジトリでの漏洩は、鍵のローテーションが必要な事故であり、履歴の消去だけでは解決しない。

## 5. 技術的ガードの設計方針

`.claude/settings.json` の permission ルールは、次の方針で構成している。

| ルール種別 | 用途 | 対応する層 |
| :- | :- | :- |
| `deny` | 承認があっても実行させない。破壊的操作、本番相当の変更、権限変更、`main` への push、PR merge | 1-a / 1-b |
| `ask` | 人間の個別承認を得て実行する。読み取り・診断を含む調査操作もここに置く | 1-c |
| `allow` | **空。** 共通配布では何も無条件許可しない。保護を `allow` に依存させない | — |

### 5-1. 共通配布の `allow` は空に保つ

**現在 `allow` は空である。** 共通配布では何も無条件許可しない。

共通配布の `allow` に入れないもの（判断基準と手順は
[../../docs/permission-policy.md](../../docs/permission-policy.md)）：

- `npm run <script>` 等、**中身がプロジェクトごとに違うもの**
  （`build` という名前で本番デプロイが走る可能性があり、名前からは判断できない）
- 依存インストール（`preinstall` / `postinstall` で第三者のコードが走る）
- テスト実行（プロジェクトのテストコードを実行する）
- フォーマッタ（Edit ツールを通らずファイルを一括で書き換える）
- `git add` の無条件許可、`git stash` 系（作業ツリーを変更する）
- 外部通信を伴うもの

**承認回数を減らすために危険な操作を無条件で許可してはならない。**

個別に必要な操作は、**各プロジェクトで中身を検証してから**
そのプロジェクトの `.claude/settings.json` または各開発者の
`.claude/settings.local.json` で**狭く**許可する（`npm run *` ではなく
`npm run test` のように特定する）。手順は上記の文書にある。
`deny` は `settings.local.json` では緩和できない。

### 5-2. `defaultMode` と編集経路

`defaultMode` は `acceptEdits`。許可範囲内のファイル編集と
`mkdir` / `touch` / `cp` 等を確認なしで進められる。
`ask` と `deny` はモードに関わらず評価されるため、`.claude/**` や
`.github/**` の編集、Git 書き込みには引き続き確認が入る。
`bypassPermissions` は使わない。
**`acceptEdits` の実機検証は未完了である。**

**編集経路ごとに保護の効き方が違う。**

- `Edit` / `Write` / `NotebookEdit` ツール → `Edit` ルールが適用される（`ask` も有効）
- `.claude/**` への書き込み → 製品側の**保護パス**でも保護される
- **Bash のリダイレクト（`> file`）と `tee` の宛先 → `ask` では止まらない**
  （`Edit` の `deny` / `allow`、保護パス、作業ディレクトリのみが検査対象）
- スクリプトが内部で開くファイル → permission ルールの適用外

したがって **設定ファイル・ルール文書をリダイレクトで書き換えてはならない。**
変更が必要なら `Edit` ツールを使い、確認を受ける。
この穴は `scope-file-guard` Hook が塞ぐ（承認範囲が無い場合も
ベースライン保護として遮断する）。

### 5-3. `ask` と自動実行は両立しない（公式仕様）

一括承認を設計するうえで決定的な制約がある。

- **`ask` ルールは `allow` ルールより優先される。**
  より具体的な `allow` ルールが一致していても、`ask` に一致すれば確認が出る。
  → `allow` で `ask` の例外を作ることはできない。
- **`PreToolUse` Hook が `"allow"` を返しても `ask` は回避できない。**
  公式ドキュメントは「Claude Code は Hook の戻り値に関わらず `deny` と `ask`
  ルールを評価する」と明記している。
  → Hook で「承認済みタスクだから自動で通す」という実装はできない。

したがって、ある操作を無人で実行させたい場合、取りうる構成は 1 つだけである。

**その操作を `ask` から外し、危険な場合を Hook の exit code 2 で遮断する。**

公式ドキュメントもこの構成を案内している
（「数個をブロックしつつ全 Bash コマンドを確認なしで実行するには、
`Bash` を `allow` に入れ、それらを拒否する `PreToolUse` Hook を登録する」）。
Hook の exit 2 は `allow` より優先されるため、遮断側が勝つ。

つまり **`ask` は「人間が見張る」方式、Hook は「機械が止める」方式**であり、
自動化は後者に移行することで実現する。両者を混ぜても自動化にはならない。

### 5-4. 現時点の選択

Hooks は実装済だが**実機セッションでの発火確認ができていない**ため、
**Git 書き込み操作（commit / push / PR 作成）は `ask` に残している。**
一括承認を宣言しても、これらは確認プロンプトが出る。

これは意図した選択である。Hook による遮断がない状態で `ask` を外すと、
承認範囲の照合も、範囲外ファイルの保護も、push 先の検査も働かないまま
Git 書き込みが通るようになる。
**「文書で一括承認を定義したこと」と「安全に自動化できること」は別である。**

移行の前提と設計は
[../../docs/ARCHITECTURE.md](../../docs/ARCHITECTURE.md) の
「承認GATE の強制（Hooks）」に記載する。

## 6. 技術的ガードの限界

permission ルールと Hooks は防御の一層であり、**単独で安全性を保証しない。**
**根拠と詳細は [../../docs/guard-limitations.md](../../docs/guard-limitations.md) にある。**

常時意識する要点：

1. **コマンド文字列の照合だけで本番環境は識別できない。**
   環境名がプロファイル・環境変数・設定ファイル側にある場合、接続文字列から
   判定が必要な場合は区別できない。
   **「本番は deny で止まる」と考えてはならない。**
   本番操作を防ぐのは 1-a の行動規範と、本番の認証情報をエージェントの
   実行環境に置かないことである。
2. **`deny` は表記の変更で回避されうる。** 絶対パス実行、ラッパーシェル
   （`bash -c`）、環境ランナー（`npx` / `docker exec`）。
   緩和策として該当経路を `ask` に置いているが網羅ではない。
3. **引数で対象を絞るパターンは脆い。** クラウド CLI の変更系 `deny` は
   網羅的な遮断ではなく、明らかな破壊操作に一段の壁を置くためのものである。
4. **`Read` / `Edit` ルールは全経路に効かない。**
   Bash のリダイレクト（`> file`）と `tee` の宛先は `Edit` の **`deny` と `allow`**
   しか検査されず、**`ask` では止まらない**。スクリプトが内部で開くファイルは
   permission ルールの適用外である。
5. **`Bash` と `PowerShell` は別ツール。** 片方だけのルールでは迂回される。
6. **ルール文書は「指示」であって「設定」ではない。** 遵守は保証されない。
   決定論的に遮断するには Hooks が必要である。
7. **Hooks も最後の砦ではない。** 設定が読み込まれないセッションでは効かない。
   既定ブランチ保護の最終的な強制力は GitHub Ruleset（サーバ側）にある。

多層防御の各層の状態は
[../../docs/guard-limitations.md](../../docs/guard-limitations.md) に記載する。

## 7. 判断に迷ったとき

**迷ったら実行しない。** STOP して、以下を人間に報告する。

1. 何をしようとしたか
2. なぜ迷ったか（どの情報が欠けているか）
3. 考えられる選択肢と、それぞれの影響範囲
4. 推奨案（根拠つき）

勝手に安全そうな方を選んで進めることも禁止する。選択は人間の判断事項である。
