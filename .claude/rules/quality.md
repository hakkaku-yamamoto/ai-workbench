# 品質ルール（quality）

対象：すべてのエージェント・スキル・セッション。
位置づけ：[../../CLAUDE.md](../../CLAUDE.md) の最上位原則 3 と 4 の詳細。

---

## 1. 変更範囲の厳守

- **指示されたファイル以外を変更しない。**
- 「ついでの修正」「気づいた改善」「フォーマット整形」は指示範囲外として扱う。
  必要だと判断した場合は、実行せずに**提案として報告する。**
- リファクタリングは、明示的に依頼されたときだけ行う。
- 依存パッケージの追加・更新・削除は、承認なしに行わない。
- 設定ファイル（`settings.json`、CI 設定、ビルド設定）の変更は、対象として明示されたときだけ行う。
- 作業開始時に「変更を許可されたファイルの一覧」を確定させ、作業終了時にそれと実際の差分を照合する。

## 2. 既存コードへの追従

- 周囲のコードと同じ書き方にする。命名規則、コメントの密度、構成、使用しているイディオムを合わせる。
- 既存の抽象化を無視して独自の方式を持ち込まない。
- 既存のライブラリで足りるものに新しいライブラリを入れない。
- 既存ファイルの編集では、全面書き換えではなく必要箇所のみを変更する。

## 3. テストと検証

- **実施していないテストを PASS と報告することを禁止する。**
- 「通るはず」「問題ないと思われる」は検証結果ではない。
- テストを実行したら、その出力を根拠として示す。失敗したら失敗したと書く。
- 実行できなかったテストは、**実行できなかったと明示する。** 省略を黙らない。
- 静的検証（構文チェック、型チェック、リンタ、JSON / YAML の妥当性）は、実行可能なら必ず実行する。
- 実行環境がない、認証がない、外部依存があるなどの理由で検証できない場合は、その理由と未検証の範囲を報告する。

### 検証レベルの区別

| レベル | 意味 |
| :- | :- |
| 実行して確認した | コマンドを実行し、出力を確認した |
| 静的に確認した | 実行せず、構文・参照・整合性を確認した |
| 未検証 | 確認していない |

報告ではこの 3 つを混ぜない。

## 4. 事実・推測・実行結果の区別

報告では以下を明確に分ける。

- **確認した事実**：ツールの出力で裏付けられる内容
- **推測・設計判断**：根拠と前提を添えて書く
- **実行結果**：実行したコマンドと、その出力

断定表現は、確認した事実にのみ使う。

## 5. 完了の定義

タスクが「完了」と言えるのは、以下を満たしたときのみ。

1. 依頼された範囲が**すべて**実装されている
2. 実行可能な検証を実行し、結果を確認した
3. 未完了・未検証の部分を特定し、明示した
4. 変更範囲が許可された範囲内に収まっている

一部だけ終わった状態を「完了」と報告しない。
範囲を縮小するかどうかは人間の判断事項である。エージェントが勝手に縮めない。

## 6. ドキュメントの整合性

- ルール文書を変更したら、相互参照のリンク先が有効であることを確認する。
- `CLAUDE.md` に詳細を書き足さない。詳細は `.claude/rules/` に置く。
- ルール間に矛盾を作らない。矛盾を見つけたら、より安全側を採用し、矛盾そのものを報告する。
- 同じ内容を複数ファイルに重複して書かない。参照で済ませる。

## 7. エラーへの対処

- エラーを握りつぶさない。
- 原因を特定せずに「リトライして通ったので OK」としない。
- 回避策で通した場合は、回避策であることと、根本原因が未解決であることを報告する。
- 失敗を繰り返す場合は、同じ手順を繰り返さず STOP して報告する。

## 8. 成果物の表記（AI 生成表記・ツール宣伝）

### 8-1. 自動挿入しないもの

成果物に以下を**依頼なしに挿入しない。**

- 「AI で作成しました」「AI生成」「Generated by AI」等の生成手段の表示
- 「Generated with \<ツール名\>」「Powered by \<ツール名\>」等のツール宣伝文言
- ツール名・モデル名を含むバッジ、ロゴ、リンク、絵文字つきの署名行
- コード冒頭の「このファイルは AI によって生成されました」コメント

対象となる成果物の例：

- ソースコード、設定ファイル、スキーマ
- README、ドキュメント、設計書
- UI 上の表示文字列、フッター、About 画面、メタタグ
- マーケティングコピー、リリースノート、ブログ記事
- 画像、デザインファイル

理由：これらは成果物の品質・内容に寄与せず、納品物に不要な情報を混ぜる。
ツール宣伝は依頼されていない広告であり、[CLAUDE.md](../../CLAUDE.md) 原則 3
（指示範囲を超えない）に反する。

### 8-2. 維持するもの

次の表示は**削除も改変もしない。**

| 種別 | 例 |
| :- | :- |
| 法令上必要な表示 | 特定商取引法の表記、景品表示法上の注記、各国の AI 生成物開示義務 |
| プラットフォーム規約上必要な表示 | 投稿先が義務づける AI 生成コンテンツのラベル、ストア審査で求められる開示 |
| ライセンス表示 | 著作権表示、ライセンス全文、NOTICE ファイル、サードパーティライセンス一覧 |
| 既存の表記 | 成果物にもともと入っていた表示（勝手に消さない） |

**8-1 と 8-2 が競合した場合は 8-2 を優先する。** 法令・規約・ライセンス上の必要性が
あるかどうか判断できない場合は、消さずに STOP して人間に確認する。

AI 生成物の開示義務は国・業種・プラットフォームによって異なり、変化する。
「不要な表記を入れない」という本節の方針を、開示義務の否定として使ってはならない。

### 8-3. 制作履歴・Git 履歴を偽装しない

- **帰属表示は制作履歴であり、宣伝文言ではない。** 両者を混同しない。
- commit の author / committer / `Co-Authored-By` 等の帰属情報を、
  実態と異なる値に書き換えない。
- 人間が書いていない変更を、人間だけが書いたように見せない。
- commit を分割・結合・改変して、誰が何をしたかの記録を曖昧にしない。
- 既存の commit 履歴を書き換えない（[github.md](github.md) 第 7 節の履歴改変の禁止）。
- 生成ツールの関与を隠すために、既にある帰属行を削除しない。

### 8-4. 判断が分かれる場合

commit メッセージや PR 本文に生成ツールの表記を入れるかどうかは、
**依頼者または組織の方針に従う。** エージェントが独断で追加も削除もしない。

- 方針が示されている場合（ハーネスの設定、組織のテンプレート、依頼者の指示）：
  その方針に従う。
- 方針が不明な場合：追加せず、必要かどうかを人間に確認する。
- 既に入っている表記を消す指示を受けた場合：それが 8-2 や 8-3 に該当しないか
  確認してから実行する。

### 8-5. 本リポジトリの組織方針（決定済）

上記 8-4 の「方針が示されている場合」に相当する、本リポジトリおよび本基盤を
再利用するリポジトリの確定方針。

| 対象 | 方針 |
| :- | :- |
| PR 本文 | **不要な AI 生成ツールの宣伝表記を自動追加しない。** 「🤖 Generated with \<ツール名\>」「Powered by \<ツール名\>」等のバッジ・署名行・リンクを入れない |
| commit の帰属情報 | **`Co-Authored-By` 等、実際の制作関与を示す帰属情報は偽装・改変しない。** 実態と異なる値に書き換えない。関与を隠すために削除しない |
| 法令・利用規約・ライセンス上の開示 | **維持する。** 8-2 の表に該当する表示は、本方針を理由に削除・省略しない |

補足：

- PR 本文には目的・変更内容・検証したこと／していないこと・レビュー観点・
  未解決事項を書く（[github.md](github.md) 第 5 節）。
  生成手段の表示はこれらに含まれない。
- 宣伝表記を入れないことと、帰属情報を残すことは**両立する。**
  前者は成果物への広告の混入を避けるためのもので、後者は制作履歴の正確さを
  保つためのものであり、目的が異なる（8-3 の冒頭を参照）。
- ハーネスやテンプレートが既定で宣伝表記を付与する設定になっている場合、
  **本方針が優先される。** PR 本文を作成する時点で宣伝表記を除く。
  一方、同じ設定が付与する `Co-Authored-By` 行は帰属情報なので残す。
- 本方針が 8-2（法令・規約・ライセンス上必要な表示）と競合した場合は、
  **8-2 を優先する。** 判断できない場合は消さずに STOP して人間に確認する。

## 9. UI/UX 設計原則

アプリ・Web サイトの画面を設計・実装する場合に適用する。

### 9-1. 汎用テンプレートの無条件採用を避ける

- 「よく使われる構成」をそのまま出力しない。
  どこにでもある AI 生成テンプレートは、対象の課題を解いていない。
- UI ライブラリや既成テーマを使う場合は、**それを選んだ理由を説明できること。**
  「無料だから」「よく使われているから」は理由にならない。
- 既成テンプレートを土台にする場合も、情報設計・導線・用語・密度を
  対象の業務に合わせて作り直す。見た目の色替えだけで済ませない。

### 9-2. 設計の前に調査する

実装を始める前に、確認できる範囲で以下を調べ、**結果を根拠として提示する。**

| 調査対象 | 具体的に見るもの |
| :- | :- |
| ブランド | 既存のロゴ、配色、タイポグラフィ、トーン＆マナー、ブランドガイドライン |
| 利用者 | 誰が使うか、使用環境（端末・回線・利用場所）、習熟度、使用頻度 |
| 業務 | 何を達成するための画面か、前後の業務フロー、頻度の高い操作、例外処理 |
| 既存デザイン | 同じ組織の既存アプリ・サイトの UI、使っているコンポーネント、命名規則 |
| 制約 | アクセシビリティ要件、対応ブラウザ・端末、既存システムとの整合 |

調査できなかった項目は、**調べていないと明示する。**
推測で埋めた部分は推測と明記する（第 4 節）。

### 9-3. 大規模な新規 UI は 3 案を比較提示する

新規画面の大規模実装（新しい画面群、主要導線の新設、デザインシステムの新規作成）
の前に、**原則 3 案**を提示し、人間がデザイン方針を承認してから実装に入る。

提示する内容：

1. 各案の設計意図（どの課題をどう解くか）
2. 情報設計・主要導線の違い
3. 9-2 の調査結果との対応（なぜこの案が対象に合うか）
4. トレードオフ（各案で何を優先し、何を捨てたか）
5. 推奨案と、その根拠

承認は [approval.md](approval.md) の「操作 × 環境 × 対象範囲」に従う。
**デザイン方針の承認は実装の承認ではない。** 実装は別途承認を得る。

3 案が成立しない場合（制約が強く選択肢が実質 1 つ、既存システムの踏襲が前提、
小規模な追加）は、**3 案を無理に作らず、成立しない理由を説明して方針を確認する。**

### 9-4. 既存アプリの改修では既存のデザインシステムを尊重する

- 既存のコンポーネント、トークン（色・余白・タイポグラフィ）、
  命名規則、レイアウト規則に合わせる（第 2 節と同じ原則）。
- **無断で全面変更しない。** 全面的な見直しが必要だと判断した場合は、
  実行せず提案として報告する（第 1 節）。
- 既存の UI と矛盾する独自ルールを持ち込まない。
- 既存デザインシステムに不足がある場合は、その不足を具体的に示し、
  追加するコンポーネント・トークンを承認を得てから作る。

### 9-5. 根拠のないブランド要素を創作しない

- **ブランドカラー、ロゴ、タグライン、世界観、ブランドストーリーを
  根拠なく作らない。** これらは組織の資産であり、デザイン上の装飾ではない。
- ブランドガイドラインが提示されていない場合は、創作せずに確認する。
- 既存の成果物から色やフォントを推定した場合は、**推定であることを明記し、
  確定値として扱わない。**
- 実在する他社のブランド要素を流用しない。
- ロゴが必要な場合は、仮のプレースホルダであることを明示する。
  それらしいロゴを作って本物のように見せない。

### 9-6. 守るべき基本品質

独自性を理由に以下を犠牲にしない。

- アクセシビリティ（コントラスト比、キーボード操作、フォーカス表示、
  代替テキスト、スクリーンリーダー対応）
- 一般的な操作慣習（利用者の既知の操作を理由なく変えない）
- レスポンシブ対応と、想定端末での実機確認
- エラー状態・空状態・読み込み中・権限不足など、**正常系以外の画面**
- 表示文字列の一貫性（同じものを別の語で呼ばない）

「独自性がある」ことと「使いにくい」ことは別である。
独自性は情報設計と業務適合で出す。基本品質を崩して出すものではない。
