# ai-workbench アーキテクチャ設計書

本書は、Claude Code のスキル・エージェント共通開発基盤の設計を定義する。
対象リポジトリ：`ai-workbench`（Public）

利用先：組織内の複数アプリケーションおよび今後の新規アプリ。
具体的な適用先アプリは本書に記載しない（Public リポジトリのため。[../.claude/rules/safety.md](../.claude/rules/safety.md) 第4節）。

### 1.3 設計方針

| 方針 | 内容 |
| :- | :- |
| 入口の単一化 | `CLAUDE.md` のみが入口。詳細は持たせない |
| 分野別分離 | ルールは分野ごとに 1 ファイル。重複させず参照で繋ぐ |
| 安全側優先 | ルールが矛盾した場合は制限が強い側を採用し、矛盾を人間に報告 |

| Public 前提 | 機密を置かない。機密が必要になったら Private 領域へ分離 |

## 2. Orchestrator の役割

Orchestrator は、人間の指示を受けて作業全体を統括する唯一のエージェントである。

### 2.1 責務

1. **タスク分解**：指示を実行可能な単位に分割する
2. **役割割り当て**：各タスクを適切な専門エージェントに割り当てる
3. **依存関係の管理**：並列実行できるものと、順序が必要なものを判別する
4. **結果の検証**：各エージェントの報告を**検証してから**次へ進む
5. **承認の仲介**：承認が必要な操作に到達したら、自分で実行せず人間に承認を求める
6. **集約報告**：全体の結果を [reporting.md](../.claude/rules/reporting.md) の形式でまとめる

### 2.2 承認範囲の引き継ぎ（一括承認の運用）

タスクスコープ承認（[../.claude/rules/approval.md](../.claude/rules/approval.md) 第 7 節）を
受けた作業では、Orchestrator が範囲の管理者になる。

```
人間
 │  タスクスコープ承認（7 項目を宣言して 1 回承認）
 ▼
Orchestrator
 │  1. 7 項目が揃っているか検証（欠けていれば作業を始めず確認）
 │  2. タスク全体を分解
 │  3. 各エージェントに「担当分の範囲」だけを引き継ぐ
 ▼
専門エージェント（Architect / UI/UX Designer / Developer / Security / Tester / Reviewer / Documenter）
 │  範囲内で作業 → 結果を返す
 │  範囲外が必要 → 実行せず Orchestrator へ報告
 ▼
Orchestrator
 │  成果物を検証 → 完了条件と照合 → 集約報告
 ▼
人間
    成果物を確認し、修正指示または取り込みを判断
```

**引き継ぎ時に各エージェントへ渡すもの**

| 項目 | 内容 |
| :- | :- |
| 担当する作業 | そのエージェントが行うこと |
| 変更を許可するファイル | **全体の範囲ではなく、担当分だけ**を渡す |
| 変更禁止の対象 | 範囲内に見えても触らないもの |
| 完了条件 | 何をもって担当分の完了とするか |
| STOP 条件 | approval.md 7-5 の 9 条件 |

**最小権限の原則**：全体の承認範囲をそのまま各エージェントに渡さない。
Developer が設定ファイルを触る必要がないなら、その範囲を渡さない。
エージェント単位のツール制限（`tools` / `disallowedTools`）も併用する（8.2 の課題 5）。

**範囲の自己拡大の禁止**

- 専門エージェントは引き継がれた範囲を超えられない。
- Orchestrator も人間が承認した範囲を超えられない。
- 複数エージェントの作業の合計が承認範囲を超えてもならない。
  各エージェントが「自分の担当分は範囲内」と判断しても、
  全体として範囲外に出ていれば違反である。この整合は Orchestrator が確認する。
- 現時点でこの照合は**エージェントの判断に依存しており、機械的に強制されていない**
  （第 9 節）。

### 2.3 制約

- 他エージェントの報告を無検証で事実として扱わない。「できた」と言われても成果物を確認する。
- エージェント間の報告が矛盾した場合、推測で調停せず人間に報告する。
- 承認が必要な操作を自分で代行しない。
- 専門エージェントの判断を上書きしない。異議がある場合は人間に報告する。

## 3. 各エージェントの責務

### 3.1 Architect（設計）

| 項目 | 内容 |
| :- | :- |
| 責務 | 要件の整理、構成設計、技術選定の提案、インターフェース定義、影響範囲の分析 |
| 成果物 | 設計書、構成図、選択肢の比較と推奨案 |
| してはならないこと | 実装を書く。承認なしに依存関係を追加する。設計の確定を自分で宣言する |

### 3.2 Developer（実装）

| 項目 | 内容 |
| :- | :- |
| 責務 | 設計に沿った実装、既存コードの様式への追従、変更範囲の厳守 |
| 成果物 | コード、ローカル差分、実装内容の説明 |
| してはならないこと | 指示範囲外のファイルを変更する。自分のコードのレビュー合否を決める。テストを通すためにテストを書き換える |

### 3.3 Security（安全性検査）

| 項目 | 内容 |
| :- | :- |
| 責務 | 秘密情報の混入検査、権限設定の検査、依存関係の脆弱性確認、入力の扱いの検査、Public リポジトリ適合性の確認 |
| 成果物 | 検出事項の一覧（重大度つき）、根拠、推奨対応 |
| してはならないこと | 自己判断で設定・権限を変更する。検出事項を軽く見せる。「問題なし」を根拠なく報告する |

### 3.4 Tester（検証）

| 項目 | 内容 |
| :- | :- |
| 責務 | テストの実行、静的検証の実行、検証範囲の明示、未実施項目の明示 |
| 成果物 | 実行したコマンドと出力、合否、未検証範囲の一覧 |
| してはならないこと | **未実施のテストを PASS と報告する。** 失敗を省略する。テストを通すために実装を書き換える |

### 3.5 Reviewer（レビュー）

| 項目 | 内容 |
| :- | :- |
| 責務 | 変更範囲の確認（許可された範囲内か）、ルール適合性の確認、設計との整合性の確認、既存コードとの一貫性の確認 |
| 成果物 | 指摘事項（根拠と該当箇所つき）、合否判定 |
| してはならないこと | コードを自分で書き直す。指摘せずに黙って修正する。merge を実行する |

### 3.6 Documenter（文書化）

| 項目 | 内容 |
| :- | :- |
| 責務 | 変更内容の文書化、ルール文書の更新、PR 本文の作成、参照リンクの整合性確認 |
| 成果物 | ドキュメント、PR 本文案 |
| してはならないこと | 実装を推測で書く。確認できない仕様を確定として書く。秘密情報を文書に含める |

### 3.7 UI/UX Designer（画面の情報設計・デザイン方針）

Developer が実装の一部として画面を作ると、
[../.claude/rules/quality.md](../.claude/rules/quality.md) 第 9 節が求める
調査・3 案比較・既存デザインシステムの尊重が省略されやすい。
そのため独立した役割として分離した。

| 項目 | 内容 |
| :- | :- |
| 責務 | 利用者・業務・ブランド・既存デザインの調査、情報設計、デザイン方針の 3 案比較提示、既存デザインシステムとの整合性確認 |
| 成果物 | 調査結果、情報設計、デザイン方針案（原則 3 案）、レビュー所見 |
| してはならないこと | 調査せずに案を出す。根拠のないブランド要素を創作する。既存デザインシステムを無断で全面変更する。デザイン方針の承認を自分で宣言する。実装まで進める |

**`Edit` / `Write` を持たない。** 方針の承認は人間が行い、実装は Developer が行う。
手順の詳細は `check-uiux` スキルにある。

### 3.8 役割境界の原則

- 自分の責務の外に出ない。他の役割の仕事を先取りしない。
- 他の役割が必要だと判断した場合は、実行せず Orchestrator へ報告する。
- 検査・検証・レビューを担当する役割は、**自分が検査した対象を自分で修正しない。**

詳細は [../.claude/rules/agent-conduct.md](../.claude/rules/agent-conduct.md) を参照する。

## 4. エージェントとスキルの違い

| 観点 | エージェント（Agent / Subagent） | スキル（Skill） |
| :- | :- | :- |
| 本質 | **役割**を持つ実行主体 | **手順**をまとめた知識 |
| 持つもの | 独立したコンテキスト、専用のシステムプロンプト、使用可能ツールの制限 | 手順書、判断基準、参照資料、補助スクリプト |
| 実行形態 | 自分で判断し、ツールを呼び、結果を返す | 呼び出した側のコンテキストに読み込まれ、その主体が手順に従う |
| コンテキスト | 親とは別。結果の要約のみが親に返る | 親と同じ。内容がそのまま文脈に加わる |
| 使いどころ | 並列化したい作業、親の文脈を汚したくない大量の読み取り、独立した判断が必要な役割 | 繰り返す定型作業、組織固有の手順、特定分野の判断基準 |
| 使い分けの目安 | 「**誰が**やるか」を分けたいとき | 「**どうやって**やるか」を揃えたいとき |
| 定義場所 | `.claude/agents/` | `.claude/skills/` |

### 4.1 組み合わせ方

エージェントとスキルは排他ではない。
**エージェントがスキルを呼ぶ**構成が基本形になる。

例：Tester エージェントが「対象アプリの回帰テスト手順」スキルを読み込んで実行する。

### 4.2 どちらにすべきか迷った場合

- 独立したコンテキストが必要か → 必要ならエージェント
- 成果物の要約だけ受け取れば十分か → 十分ならエージェント
- 手順を複数の役割で共有したいか → 共有したいならスキル
- 親の文脈で判断を続ける必要があるか → 必要ならスキル

## 5. 共通ルールの適用範囲

### 5.1 階層

| 層 | 定義場所 | 適用範囲 |
| :- | :- | :- |
| 会社共通ルール | 本リポジトリ `CLAUDE.md` + `.claude/rules/` | 全アプリ・全エージェント |
| アプリ固有ルール | 各アプリリポジトリの `CLAUDE.md` | そのアプリのみ |
| 個人設定 | `.claude/settings.local.json`（Git 管理外） | その人のその環境のみ |

### 5.2 優先順位

1. 会社共通ルールの「絶対禁止」は、どの層からも上書きできない
2. アプリ固有ルールは、会社共通ルールを**厳しくする方向にのみ**上書きできる
3. 緩める方向の上書きは認めない
4. 矛盾が生じた場合は、より安全側を採用し、矛盾そのものを人間に報告する

### 5.3 ルールの読み込み機構（設計の成立根拠）

この設計が機能するのは、Claude Code が以下のように動作するためである。
改変するときはこの前提を壊さないこと。

- **`.claude/rules/` 配下の `.md` ファイルは、`paths` frontmatter を持たない場合、
  起動時に無条件で読み込まれる**（`.claude/CLAUDE.md` と同じ優先度）。
  再帰的に探索されるため、サブディレクトリも対象になる。
  本リポジトリの 6 ファイルはいずれも frontmatter を持たないため、毎セッション読み込まれる。
- `paths` frontmatter を付けると、該当するファイルを Read / Write / Edit したときのみ
  読み込まれる**条件付きルール**になる。常時適用したいルールには付けない。
- **サブエージェントは CLAUDE.md 階層を継承する**（`~/.claude/CLAUDE.md`、
  プロジェクトの `CLAUDE.md`、`CLAUDE.local.md`、管理ポリシー、`AGENTS.md`）。
  組み込みの Explore / Plan エージェントは除く。
  カスタムエージェントは `omitClaudeMd: true` で除外できるため、**使わない。**
- **サブエージェントは親の permission ルールを継承する。**
  `.claude/settings.json` の `deny` / `ask` はサブエージェントのツール呼び出しにも適用される。
  設定ファイルの Hooks もサブエージェント内で発火する。
- **`.claude/rules/` がサブエージェントに届くかは公式ドキュメントに明記がなく、未検証である。**
  このため、全エージェントに確実に届かせたい禁止事項は `CLAUDE.md` 側にも記載する。
  STEP 3 でエージェントを実装する際に実機検証する。
- スキルは呼び出した主体のコンテキストに読み込まれるため、
  既にコンテキストにあるルールがそのまま適用される。

### 5.4 コンテキスト消費

`CLAUDE.md` と `.claude/rules/` は毎セッション読み込まれるため、常時コンテキストを消費する。
エージェント・スキルの追加に伴って増加するため、STEP 3 / STEP 4 の実装時に再測定し、
局面限定のルール（例：報告時のみ必要なもの）をスキル化するか、
`paths` frontmatter で条件付き読み込みにするかを判断する。

#### UI/UX 専門ルールの移行方針

[../.claude/rules/quality.md](../.claude/rules/quality.md) 第 9 節（UI/UX 設計原則）は、
**画面を設計・実装するときにのみ必要**な性質であり、常時読み込みの第一の削減候補とする。
将来的に次のいずれかへ移行し、コンテキスト消費を抑える。

| 移行先 | 方式 | 読み込まれるタイミング | 向いている場合 |
| :- | :- | :- | :- |
| スキル | `.claude/skills/` へ切り出す | 呼び出したとき、または Claude が関連すると判断したとき | 手順として独立させたい。画面開発の頻度が低い |
| 条件付きルール | `paths` frontmatter を付けた `.claude/rules/` のファイルに分離する | 該当するファイル（UI のソース等）を Read / Write / Edit したとき | ルールとして常に効かせたいが、画面に触るときだけでよい |

移行時の注意：

- **第 9 節を削除するだけにしない。** 移行先を用意してから外す。
  移行先がない状態で外すと、画面開発時にルールが適用されなくなる。
- `paths` frontmatter で分離する場合、対象パターンは各アプリのディレクトリ構成に
  依存する。本リポジトリ側で固定せず、配布先ごとに設定できる形を検討する。
- スキル化する場合、[../.claude/rules/quality.md](../.claude/rules/quality.md) 9-3
  の「大規模な新規 UI では 3 案を提示して承認を得る」は、スキルを呼ばなければ
  適用されない。**スキルが呼ばれなかった場合に抜け落ちないよう**、
  この一点だけは `CLAUDE.md` または常時読み込みのルールに残すことを検討する。
- 移行の判断時期は STEP 3 / STEP 4。本工程では実施しない。

現時点で第 9 節は約 4.9 KB（`quality.md` 全体の約 34%）を占める。
移行の検討事項は 8.4.3 の項目 8 に記録する。

### 5.5 Claude Code の設定優先順位との関係

Claude Code の `settings.json` は以下の優先順位で解決される（高い順）。

1. Managed settings（組織配布）
2. コマンドライン `--settings`
3. `.claude/settings.local.json`（個人・Git 管理外）
4. `.claude/settings.json`（共有・Git 管理）
5. `~/.claude/settings.json`（ユーザー個人）

**注意点：**

- `permissions.allow` / `permissions.ask` / `permissions.deny` の各リストは、上書きではなく**マージ**される。
- `permissions.allow` と `permissions.additionalDirectories` は、**ワークスペースの信頼（trust）を承認するまで適用されない。**
- `permissions.deny` と `permissions.ask` は**即時適用される。**
- このため本リポジトリの `settings.json` は、**保護を `deny` と `ask` だけで成立させている。**
  `allow` は**空**であり、共通配布では何も無条件許可しない。
  trust 承認が得られない環境では `allow` が効かず確認プロンプトが増えるが、
  **保護の強さは変わらない。** 共有ファイルで確実に効く手段に保護を依存させる設計である。
- **プロジェクトごとに中身が違う操作は共通配布の `allow` に入れない。**
  `npm run <script>`、依存インストール、テスト実行などは、各プロジェクトで
  中身を検証してから、そのプロジェクトの設定で狭く許可する
  （[../.claude/rules/safety.md](../.claude/rules/safety.md) 5-1、[permission-policy.md](permission-policy.md)）。

**個別の許可は各開発者の `.claude/settings.local.json` で持つ。**
`ask` の確認プロンプトが業務上過剰だと感じる操作（例：`npx tsc --noEmit` のような
静的検証コマンド）は、各自が `settings.local.json` の `allow` に追加する。
このファイルは Git 管理外（`.gitignore` 済）であり、未追跡のままなら trust 承認なしに
`allow` が適用される。

ただし **`deny` は `settings.local.json` では緩和できない。**
`deny` は `allow` より優先され、`allow` で例外を作れない。
業務上必要な操作が `deny` に入っている場合は、共有ファイル側の修正が必要になるため、
人間に報告する。

## 6. 他リポジトリへ配布する方法

本工程では実装しない。方式は公式仕様の確認結果に基づいて決定した。

### 6.1 前提：Plugin はルールを配布できない

Claude Code のプラグインが配布できるコンポーネントは、公式ドキュメントによれば以下である。

- Skills（`SKILL.md`）
- Agents（サブエージェント定義）
- Hooks
- hooks module（mod）
- MCP servers

**`CLAUDE.md` 形式の指示文と `.claude/rules/` ファイルは含まれていない。**
したがって本基盤の中核である共通ルールは、Plugin では配布できない。

加えて、クラウドセッションはローカル設定の Plugin を読み込まない。

このため、**ルールの配布と実行コンポーネントの配布を分ける。**

### 6.2 ルール（CLAUDE.md + .claude/rules/）の配布

| 方式 | 概要 | 利点 | 欠点 | 採否 |
| :- | :- | :- | :- | :- |
| **同期スクリプト** | 本リポジトリから各アプリへファイルをコピーし、CI で原本との差分を検査する | 依存がなく、どの環境でも確実。Windows の権限問題がない。各リポジトリに実体があるため追跡性が高い | コピーが散る。行き渡りを仕組みで担保する必要がある | **第一候補** |
| **シンボリックリンク** | 各プロジェクトの `.claude/rules/` から共有ルールへリンク。公式にサポートされている（循環リンクも検出される） | 原本が 1 つ。更新が一元化される | プロジェクトごとに 1 回の承認ダイアログが必要。Windows では開発者モードまたは管理者権限が必要。UNC 等のネットワークパスを指すリンクは読み込まれない | 代替 |
| **`~/.claude/rules/`** | 端末のユーザー領域に置き、全プロジェクトへ適用。承認ダイアログが不要 | 導入が容易。即時に全プロジェクトへ適用 | 端末ごとのセットアップが必要。リポジトリとの紐づけがなくなり、新しい端末・新しい開発者で漏れる | 代替 |
| **Git Submodule** | `.claude/rules/` を submodule として参照 | バージョン固定が容易 | 運用コストが高く、更新忘れが起きやすい | 不採用 |
| **手動コピー** | 都度コピー | 導入が即時 | 更新が行き渡らない。実質的に管理不能 | 不採用 |

**第一候補は同期スクリプト。** 理由：

1. Windows / macOS / Linux のいずれでも追加権限なしに動作する
2. 各リポジトリにファイルの実体が残るため、どのバージョンが適用されているか追跡できる
3. CI で原本との差分を検査すれば、更新の行き渡りを機械的に担保できる

### 6.3 エージェント・スキル・Hooks の配布

**Plugin 方式を検討する。** これは Plugin が本来対象とするコンポーネントである。

- marketplace 経由で配布し、project スコープで有効化すると、
  コミット済みの `.claude/settings.json` を通じてチーム全員に行き渡る。
- ただし各開発者が自分の端末にインストールする必要がある。
- クラウドセッションではローカル設定の Plugin が読み込まれないため、
  クラウドを使う場合は別途の対応が必要になる。

実装は STEP 5。採用前に Plugin の manifest 仕様と marketplace の運用方法を確認する。

### 6.4 配布先の前提条件

配布先の各リポジトリは、作業開始前に以下を満たしていること。

1. `main` に相当する既定ブランチが保護されている（PR 必須・削除禁止・force push 禁止）
2. その保護が Active であることを確認できる
   （確認手段は `gh ruleset list` / `gh api .../rulesets`。いずれも `ask` で実行できる）
3. 秘密情報がリポジトリに置かれていない
4. 機密を扱う場合は Private であること

満たさない場合は、作業せず `BLOCKED` で報告する。

### 6.5 配布前に解消しておくべきこと

`deny` ルールは `allow` で例外を作れないため、過剰な `deny` は配布先で回避不能な障害になる。
配布後の修正は全リポジトリへの再配布が必要になるため、**配布前に `deny` / `ask` の
妥当性を確定させる。**

2. バージョニング方針（原本の更新をどう取り込み、どのバージョンが適用されているかを確認するか）
3. クラウドセッションで `.claude/rules/` が読み込まれるかの検証（未確認）

## 7. セキュリティ方針

### 7.1 Public リポジトリとしての制約

このリポジトリは Public である。以下を置かない。

- API キー、トークン、OAuth シークレット
- パスワード、秘密鍵、証明書の秘密部分
- 本番 DB 接続情報
- 非公開の会社情報、社内固有の業務ルール、取引先名
- **社内アプリ・社内プロダクトの名称**（公開済みであると確認できないもの）
- 組織の内部構造、部署名、担当者名
- 個人情報
- 機密性のある業務データ
- 本番環境固有の秘密設定、内部ホスト名・IP・URL

本書および共通ルールは、適用先アプリを一般化した表現（「組織内の複数アプリケーション」
「対象アプリは別途決定」）で記述している。実名は Private 領域に置く。

許可されるもの：`.env.example` 等のプレースホルダ、ローカル開発専用のダミー値、
一般化された記述。

### 7.2 機密ルールの分離設計

会社固有の機密ルールが必要になった場合、本リポジトリに追記せず分離する。

```
ai-workbench（Public）
  └─ 一般化された共通ルール、設計、エージェント／スキルの骨格

ai-workbench-private（Private・将来）
  └─ 社内固有の業務ルール、環境固有の設定、取引先・顧客に関わる判断基準、
     適用先アプリの実名とアプリ固有の運用ルール
```

分離の原則：

- Public 側には**仕組み**を置く。Private 側には**内容**を置く。
- Public 側のルールは、Private 側がなくても単独で成立すること。
- Private 側は Public 側を参照してよいが、逆方向の参照は作らない。
- 秘密の実値はどちらにも置かない。環境変数または秘密情報管理サービスから読む。

### 7.3 多層防御

| 層 | 強制力 | 状態 |
| :- | :- | :- |
| GitHub Ruleset（`protect-main`） | サーバ側で強制。回避不能 | **設定済・Active**（PR 必須 / 削除禁止 / force push 禁止、bypass actor なし） |
| 最小権限の認証 | トークンのスコープで制限。**本番の認証情報をエージェントの実行環境に置かない** | 未整備（次工程） |
| permission ルール（`settings.json`） | セッション内の事故防止。善意の誤操作を止める | **設定済** |
| Hooks（`PreToolUse` 等） | 決定論的に遮断。exit code 2 でツール呼び出しを停止 | **実装・登録済**（第 11 節）。ただし実機セッションでの発火は未確認（11-5） |
| ルール文書（`CLAUDE.md` / `.claude/rules/`） | エージェントの判断基準。コンテキストとして渡される指示であり、遵守は保証されない | **設定済** |
| 人間の承認 | 最終的な責任の所在 | 常時 |

#### permission ルールの設計方針

| ルール種別 | 用途 |
| :- | :- |
| `deny` | 承認があっても実行させない層。破壊的操作、本番相当の変更、権限変更、`main` への push、PR merge |
| `ask` | 人間の個別承認を得て実行する層。読み取り・診断を含む調査操作もここに置く |
| `allow` | **空。** 共通配布では何も無条件許可しない。承認削減は Auto モードと必要最小限の Hooks で実現する（第 10 節） |
| `defaultMode` | `acceptEdits`。許可範囲内のファイル編集と `mkdir` / `touch` / `cp` 等を確認なしで進める。`ask` と `deny` はモードに関わらず評価されるため、保護は弱まらない。配布時の前提条件は第 10 節 |

**共通配布の `allow` に入れないもの**：`npm run <script>` 等のプロジェクト定義
スクリプト、依存インストール（`preinstall` / `postinstall` が走る）、
テスト実行、フォーマッタ、`git add` の無条件許可、`git stash` 系、外部通信。
理由と代替手段（プロジェクト固有の事前検証方式）は
[../.claude/rules/safety.md](../.claude/rules/safety.md) 5-1 と [permission-policy.md](permission-policy.md) に記載する。

**読み取り専用の操作を `deny` に入れない。**
`deny` は `allow` で例外を作れないため、承認による回復手段と、
各開発者の `settings.local.json` による緩和手段が失われる。

#### permission ルールの限界

**permission ルールは単独で安全性を保証しない。**
特に、**コマンド文字列の照合だけで本番環境を識別することはできない。**
環境名がプロファイル・環境変数・設定ファイル側にある場合、接続文字列から判定が必要な場合、
同じコマンドが環境によって異なる対象を指す場合は、照合で区別できない。

本番環境の操作を防ぐのは、行動規範（[../.claude/rules/safety.md](../.claude/rules/safety.md) 1-a）と、
**人間が本番の認証情報をエージェントの実行環境に置かないこと**である。
`deny` パターンは「明らかな本番操作に一段の壁を置く」補助に過ぎない。

その他の既知の限界（表記変更による deny 回避、引数パターンの脆さ、
Read/Edit ルールの適用範囲、`.env.*` 列挙の非網羅性、PowerShell の引数位置、
環境ランナーの素通し）は
[../.claude/rules/safety.md](../.claude/rules/safety.md) 第 6 節に記載する。

### 7.4 Windows 11 での運用

- Claude Code の `Bash(...)` と `PowerShell(...)` は**別のツール**であり、permission ルールも別に書く必要がある。
  本リポジトリの `settings.json` は両方を記述している。
- `PowerShell` ルールはエイリアスが正規化されるため、`PowerShell(Remove-Item *)` は
  `rm` / `del` / `rd` / `erase` / `ri` / `rmdir` も対象になる。
  この性質により `Remove-Item` を一括 `deny` にすると、PowerShell からの
  ファイル削除が一切できなくなる。PowerShell はこの環境の主シェルであるため、
  `settings.json` では**再帰削除のみを `deny`、単一ファイル削除は `ask`** としている。
  Bash 側（`rm -r` 系が `deny`、`rm *` が `ask`）と可否を揃えてある。
  ただし PowerShell は引数の位置が自由なため、`-Recurse` の位置を
  パターンで捉えきれない組み合わせが残る。
- パスは照合前に POSIX 形式へ正規化される（`C:\Users\x` が `/c/Users/x` になる）。
  絶対パスのルールを書く場合は `//c/**` 形式を使う。
- `~/.claude` は `%USERPROFILE%\.claude` を指す。
- `.gitignore` に Windows 固有の生成物（`Thumbs.db`、`desktop.ini`、`$RECYCLE.BIN/`、`*.lnk`）を含めている。
- `.gitattributes` で改行コードを統一している。リポジトリ内は LF に正規化し、
  Windows 専用スクリプト（`.ps1` / `.psm1` / `.bat` / `.cmd`）は CRLF で取り出す。
  これがないと各開発者の `core.autocrlf` 設定に依存し、
  複数環境へ配布したときに差分ノイズが発生する。
- 配布方式にシンボリックリンク（6.2）を選ぶ場合、Windows では
  **開発者モードの有効化または管理者権限が必要**になる。
  また UNC 共有（`\\server\share`）などのネットワークパスを指すリンクは読み込まれない
  （`\\wsl$` はネットワークパス扱いにならない）。
  この制約があるため、6.2 では同期スクリプトを第一候補としている。

### 8.1 STEP 2（Hooks）の実装候補

本工程では Hooks を作成しない。次工程の候補として以下を記録する。
**承認GATE の強制を含めた全体設計は第 9 節にある。** 以下はその一部である。

| Hook | イベント | 目的 | 想定動作 |
| :- | :- | :- | :- |
| `block-main-push` | `PreToolUse`（Bash / PowerShell） | `main` への push を文字列パターンに依存せず遮断 | コマンドを解析し、push 先が既定ブランチなら exit 2 |
| `block-force-push` | `PreToolUse`（Bash / PowerShell） | force push の遮断 | `--force` / `-f` / `+refspec` を検出し exit 2 |
| `secret-scan` | `PreToolUse`（Edit）/ `PostToolUse` | 秘密情報の混入検知 | 鍵・トークンのパターンを検査し、該当したら exit 2 |
| `scope-guard` | `PreToolUse`（Edit） | 指示範囲外のファイル変更の遮断 | 許可パスの一覧と照合し、範囲外なら exit 2 |
| `no-auto-merge` | `PreToolUse`（Bash / PowerShell） | PR の自動 merge の遮断 | `gh pr merge` を検出し exit 2 |
| `absolute-path-guard` | `PreToolUse`（Bash） | 絶対パス指定による deny 回避の遮断 | `/usr/bin/` 等の絶対パス実行や `sh -c` ラッパーを検出 |

**設計上の注意：**

- Hooks は exit code 2 で停止でき、permission の `allow` ルールよりも優先される（ツール呼び出し前に止まる）。
  一方、`deny` / `ask` ルールは Hook の判断にかかわらず評価されるため、両者は補完関係にある。
- Hook は**コマンド文字列の解析**を行うため、permission のパターン照合より堅牢にできるが、完全ではない。
- Windows 11 と POSIX シェルの両方で動作するよう、実装言語と起動方法を検討する必要がある。
- Hook 自体がリポジトリ内のスクリプトであるため、Hook ファイルの変更を保護する設計が必要になる。

## 9. 承認GATE の強制（Hooks）

[../.claude/rules/approval.md](../.claude/rules/approval.md) 第 7 節のタスクスコープ承認を、
文書上の方針から**機械的に強制される仕組み**へ移すための設計。
**本工程では実装しない。** STEP 2 の対象である。

### 9.1 なぜ Hooks が必要か（`ask` では自動化できない）

公式仕様に 2 つの決定的な制約がある。

1. **`ask` は `allow` より優先される。**
   より具体的な `allow` が一致していても、`ask` に一致すれば確認が出る。
2. **`PreToolUse` Hook が `"allow"` を返しても `ask` は回避できない。**
   Claude Code は Hook の戻り値に関わらず `deny` と `ask` を評価する。

したがって「`ask` を残したまま、Hook が承認済みタスクだと判定して自動で通す」
という実装は**成立しない。**

取りうる構成は 1 つである。

| 現在（`ask` 方式） | 移行後（Hook 方式） |
| :- | :- |
| Git 書き込みを `ask` に置き、**人間が見張る** | Git 書き込みを `ask` から外し、**Hook が exit 2 で止める** |
| 自動化できない | 範囲内なら自動で進み、範囲外は機械的に止まる |
| 範囲の照合はエージェントの判断 | 範囲の照合は Hook のコード |

公式ドキュメントもこの構成を案内している
（「数個をブロックしつつ全 Bash コマンドを確認なしで実行するには、
`Bash` を `allow` に入れ、それらを拒否する `PreToolUse` Hook を登録する」）。
Hook の exit 2 は `allow` より優先されるため、遮断側が必ず勝つ。

**この移行は「保護を外す」ことではなく「保護の実装を人間から機械へ移す」ことである。**
Hook が先に動いていなければ、`ask` を外してはならない。

### 9.2 承認済みタスクの表現

Hook が照合するための、承認範囲の機械可読な表現が必要になる。

| 項目 | 用途 |
| :- | :- |
| タスク ID | どの承認かを特定する |
| 対象リポジトリ（`owner/repo`） | 他リポジトリへの操作を遮断する |
| 作業ブランチ | push 先の照合に使う |
| base ブランチ | PR 作成時の照合に使う |
| 変更を許可するパスのパターン | 対象外ファイルへの変更を遮断する |
| 変更禁止のパスのパターン | 許可パターンより優先して遮断する |
| 許可する Git 操作（commit / push / PR 作成） | 承認に含まれない操作を遮断する |
| 完了条件・テストコマンド | commit 前のテスト実行確認に使う |
| 有効期限または失効条件 | 承認の使い回しを防ぐ |

**置き場所の検討事項**：
リポジトリ内に置くとエージェント自身が書き換えられてしまう。
`.claude/` 配下に置く場合、Hook ファイルと承認ファイルの両方を
変更から保護する設計が必要になる（9.5）。

### 9.3 実装する Hook（検討内容）

| Hook | イベント | 遮断する対象 | 判定方法 |
| :- | :- | :- | :- |
| `scope-repo-guard` | `PreToolUse`（Bash / PowerShell） | 承認外リポジトリへの操作 | `git remote get-url origin` と承認の対象リポジトリを照合。不一致なら exit 2 |
| `scope-branch-guard` | `PreToolUse`（Bash / PowerShell） | 承認外ブランチへの push | push コマンドを解析し、push 先 ref と承認の作業ブランチを照合 |
| `block-main-push` | `PreToolUse`（Bash / PowerShell） | 既定ブランチへの直接 push | 文字列パターンに依存せず、push 先が既定ブランチなら exit 2。`git -C` や絶対パス経由も対象にする |
| `block-force-push` | `PreToolUse`（Bash / PowerShell） | force push | `--force` / `-f` / `--force-with-lease` / `+refspec` を解析して exit 2 |
| `scope-file-guard` | `PreToolUse`（Edit / Write / NotebookEdit / **Bash / PowerShell**） | 対象外ファイルへの変更 | 変更先パスを承認の許可パターン・禁止パターンと照合。禁止パターンを優先。**加えて Bash のリダイレクト（`> file` / `>> file`）と `tee` の宛先、フォーマッタ等の一括書き換えも検査する**（これらは `Edit` の `ask` では止まらない。第 10 節 10-4） |
| `secret-scan-precommit` | `PreToolUse`（Bash / PowerShell：commit / push） | 秘密情報の混入 | ステージ内容または差分を検査。**大文字小文字を区別しない**（過去にこの欠落で検出漏れが発生した）。社内固有名のリストも照合 |
| `test-gate-precommit` | `PreToolUse`（Bash / PowerShell：commit） | テスト未実行・失敗のままの commit | 承認のテストコマンドが実行され成功した記録があるかを確認。なければ exit 2 |
| `pr-target-guard` | `PreToolUse`（Bash / PowerShell：`gh pr create`） | 承認外の base / リポジトリへの PR | base と head、対象リポジトリを承認と照合。差分ファイルが許可範囲内かも確認 |
| `stop-condition-guard` | `PreToolUse` / `PostToolUse` | STOP 条件の自己解除 | approval.md 7-5 の条件に触れる操作を検出。該当したら exit 2 し、エージェントが続行できないようにする |
| `no-auto-merge` | `PreToolUse`（Bash / PowerShell） | PR の merge・auto-merge 有効化 | `gh pr merge`、`gh api` の merge 系、auto-merge 設定を検出して exit 2 |

### 9.4 Windows 11 での考慮事項

- **`Bash` と `PowerShell` は別ツールであり、Hook はどちらのイベントでも
  発火させる必要がある。** 片方だけでは迂回される。
- PowerShell はエイリアスが正規化されるため、Hook 側でも
  `rm` / `del` / `ri` などを `Remove-Item` と同一視して解析する必要がある。
- PowerShell は引数の位置が自由であり、`-Recurse` の位置を前提にできない。
  文字列の前方一致ではなく、トークン単位の解析が必要になる。
- **コマンドラッパー経由の迂回**を考慮する。
  `bash -c` / `sh -c` / `cmd /c` / `powershell -Command` / 絶対パス実行
  （`/usr/bin/git`、`C:\Program Files\Git\bin\git.exe`）/ `npx` / `docker exec` /
  環境ランナー。Hook はコマンド文字列を再帰的に展開して解析する。
- Hook の実装言語は Windows と POSIX の両方で動くものを選ぶ
  （Node.js または Python。シェルスクリプトは避ける）。
- パスは照合前に正規化する。Claude Code は POSIX 形式へ正規化するが、
  Hook が受け取る値の形式を確認してから実装する。
- 改行コードは `.gitattributes` で LF に統一済だが、Hook が標準入力から
  受け取る JSON の改行も考慮する。

### 9.5 Hook 自体の保護

Hook がリポジトリ内のファイルである限り、エージェントが書き換えられる。
これを防ぐ設計が必要である。

- `.claude/hooks/**` と承認ファイルを `Edit` の `deny` に入れる
  （現在 `.claude/**` は `ask`。Hook 導入時に `deny` へ変更するかを判断する）。
- `.claude/settings.json` 自体の変更も `deny` にするかを判断する。
  ただし `deny` にすると、人間が Claude Code 経由で設定を直せなくなる。
- `--settings` や `CLAUDE_CONFIG_DIR` による設定の差し替え、
  `--disable-all-hooks` 相当のフラグによる Hook 無効化を考慮する。
  公式仕様で `disableAllHooks` はプロジェクト設定で上書きできるため、
  完全な固定には管理設定（managed settings）が必要になる。
- **最終的な強制力は GitHub Ruleset（サーバ側）にある。**
  ローカルの Hook を無効化できたとしても、既定ブランチの保護は破れない。
  Hook は「事故を手前で止める」層であり、最後の砦ではない。

### 9.6 移行の前提条件

次がすべて満たされるまで、Git 書き込み操作を `ask` から外さない。

1. 9.3 の Hook のうち、少なくとも `scope-repo-guard`、`scope-branch-guard`、
   `block-main-push`、`block-force-push`、`scope-file-guard`、
   `secret-scan-precommit` が実装され、動作確認されている
2. 承認範囲の機械可読な表現（9.2）が確定し、改ざんから保護されている
3. Hook が Windows の `Bash` / `PowerShell` の両方で発火することを実機確認した
4. Hook の迂回経路（9.4）を評価し、残存リスクを文書化した
5. Hook が失敗・未起動のときに**安全側に倒れる**（操作を通さない）ことを確認した
6. GitHub Ruleset の必要承認数が引き上げられている

**1〜6 が未達の状態で `ask` を外すことは、保護の削除にあたる。**
文書上の方針だけで「自動承認が実現した」と報告してはならない。

## 10. 標準機能の調査結果（Auto モード・Sandbox）

独自 Hooks の必要範囲を見直すため、Claude Code の標準機能を調査した
（READ ONLY。有効化は行っていない）。

調査時点：Claude Code **2.1.296**（npm-global / win32-x64 / native Windows）

### 10-1. Auto モード

| 項目 | 結果 |
| :- | :- |
| 利用可否（プラン） | **全プランで利用可能** |
| 利用可否（モデル） | Anthropic API では Opus 4.6+ / Sonnet 4.6+ / Haiku 5.5 / Fable。**本環境のモデルは条件を満たす** |
| Windows 対応 | native Windows では **v2.1.233 以降**が必要。本環境は 2.1.296 のため**対応している** |
| 有効化方法 | `claude --permission-mode auto`、または `~/.claude/settings.json` の `permissions.defaultMode` |
| **プロジェクト設定から指定できるか** | **できない。** `.claude/settings.json` / `.claude/settings.local.json` の `"auto"` は効かず、組み込み既定に戻る |

**仕組み**：分類器モデル（既定 Claude Sonnet 5）が、人間の代わりに
各操作を事前審査する。判定順は
(1) allow / ask / deny ルール → (2) 読み取りと作業ディレクトリ内の編集は自動承認
（保護パスへの書き込みと作業ディレクトリ外の初回読み取りを除く）→
(3) それ以外は分類器 → (4) 分類器が拒否した場合は理由が返る。
分類器はツール結果を見ない（ファイルや Web の敵対的内容に操作されない設計）。
3 回連続または累計 20 回の拒否で auto モードは一時停止する。

**既定で拒否される操作の例**：`curl | bash` によるコード取得実行、
外部エンドポイントへの機密データ送信、本番デプロイとマイグレーション、
force push、`git reset --hard`、`terraform destroy`、
未承認 PR の merge、認証情報の出力。

**既定で許可される操作の例**：作業ディレクトリ内のファイル操作、
ロックファイル・マニフェストに宣言された依存のインストール、
読み取り専用 HTTP、**作業リポジトリのブランチへの push**
（`production` や `gh-pages` のようなデプロイ対象を示す名前のブランチを除く）。

**本基盤にとって決定的な点（3 つ）**

1. **`ask` ルールは auto モードでもプロンプトを出す。**
   公式ドキュメントは「`Bash(git push *)` のようにコマンド内容に対する
   ask ルールはプロンプトにフォールバックする」と明記している。
   → **auto モードを使っても、現在の `ask` を残したままでは
     Git 書き込みは自動化されない。** Hooks と同じ結論である。
2. **auto モードに入ると広い `allow` ルールは無効化される。**
   `Bash(*)` / `PowerShell(*)`、`Bash(python*)` のようなインタプリタの
   ワイルドカード、**パッケージマネージャの run コマンド**、`Agent` ルール、
   `Monitor` ルールが対象。`Bash(npm test)` のような狭いルールは残る。
   → STEP 1J で `allow` に入れた `npm run build*` 等は、
     **製品側が auto モードで自動的に落とすカテゴリ**だった。
     今回これらを共通配布から外した判断は、この挙動と一致する。
3. **プロジェクト設定から有効化できない。**
   → 共通ルールとして `settings.json` で配布することはできない。
     各開発者の `~/.claude/settings.json` または起動時フラグで選ぶ運用になる。
     **組織全体へ強制することも、逆に共通ファイルで固定することもできない。**

**無効化**：`permissions.disableAutoMode` を `"disable"` にすると使えなくなる。
本リポジトリでは設定していない（auto モードでも `deny` / `ask` は評価されるため、
保護は維持される）。

### 10-2. Sandbox

| 項目 | 結果 |
| :- | :- |
| **native Windows での利用可否** | **利用できない。** 公式ドキュメントは「native Windows では Claude Code はコマンドをサンドボックスなしで実行する」と明記。使うには **WSL2 内で Claude Code を動かす**必要がある |
| 対応 OS | macOS / Linux / WSL2 |
| 既定 | 無効 |
| 有効化 | `/sandbox`、または `sandbox.enabled` を `true` |
| 依存（Linux / WSL2） | `bubblewrap` と `socat` |
| 保護範囲 | **シェルコマンドのみ。** 書き込みは作業ディレクトリ・ユーザー一時ディレクトリ・追加ディレクトリに限定され、保護パスは書き込み拒否のまま |
| サンドボックス外 | **Read / Edit / Write / WebFetch などの組み込みツール、Hooks、MCP サーバ、LSP、ステータスライン、`apiKeyHelper`** |
| `autoAllowBashIfSandboxed` | 既定 `true`。サンドボックス内のコマンドは確認なしで実行される。Manual モードでもファイルを変更するコマンドが通る |
| `ask` との関係 | 丸ごとの `Bash` ask は代替されるが、**`Bash(git push *)` のような内容指定の ask は依然としてプロンプトを出す** |

**本環境（native Windows）では Sandbox を安全装置として使えない。**
WSL2 へ移行すれば `autoAllowBashIfSandboxed` により
「シェルコマンドの副作用を OS が封じ込めつつ無確認で実行する」構成が取れるが、
それでも内容指定の `ask` は残り、組み込みファイルツールと Hooks は
サンドボックス外である。

### 10-3. 標準機能で代替できる独自 Hooks と、できないもの

| 第 9 節の Hook | 標準機能で代替できるか |
| :- | :- |
| `block-force-push` | **auto モードが既定で拒否**（force push は拒否リストにある）。ただし auto モードは任意利用であり強制できない。`deny` ルールでの遮断を併用する（実装済） |
| `no-auto-merge` | **auto モードが既定で拒否**（未承認 PR の merge）。同様に `deny` を併用（実装済） |
| 本番デプロイ・マイグレーションの遮断 | **auto モードが既定で拒否。** `deny` ルールと併用（実装済） |
| `secret-scan-precommit` | auto モードは外部エンドポイントへの機密送信を拒否するが、**commit 内容の秘密情報検査は行わない。独自 Hook が必要** |
| `scope-repo-guard` / `scope-branch-guard` | auto モードは「作業リポジトリのブランチへの push」を既定で許可する。**どのリポジトリ・どのブランチが承認済みかは分類器が知らない。独自 Hook が必要** |
| `scope-file-guard` | auto モードは作業ディレクトリ内の編集を既定で自動承認する。**承認範囲という概念を持たない。独自 Hook が必要** |
| `test-gate-precommit` | **代替なし。独自 Hook が必要** |
| `pr-target-guard` | **代替なし。独自 Hook が必要** |
| `stop-condition-guard` | **代替なし。独自 Hook が必要** |
| `block-main-push` | Sandbox は無関係。auto モードは「デプロイ対象を示す名前のブランチ」を除外するが、既定ブランチ全般の保護ではない。`deny` ルールと **GitHub Ruleset** で担保（実装済）。パターン非依存の遮断には独自 Hook が必要 |

**結論**：標準機能は「一般的に危険な操作」を止めるが、
**「このタスクで承認された範囲」という概念を持たない。**
一括承認の強制に必要な Hook（repo / branch / file / test / pr-target /
stop-condition / secret-scan）は、標準機能では代替できない。

一方で、`block-force-push` / `no-auto-merge` / 本番デプロイ遮断は
`deny` ルール（実装済）と auto モードの既定拒否で二重に守られるため、
**独自 Hook の優先度を下げられる。**
第 9 節 9.6 の必須 Hook は、この結果を踏まえると
`scope-repo-guard` / `scope-branch-guard` / `scope-file-guard` /
`secret-scan-precommit` の 4 つが最優先である。

### 10-3-a. 承認削減の方針（確定）

1. **標準 Auto モードを優先して評価する。** 独自実装より先に標準機能を試す。
2. **タスク固有の承認範囲は必要最小限の Hooks で保護する**（上記 4 つ）。
3. **Git 書き込みの `ask` は、安全装置の実機検証が完了するまで維持する。**
4. **共通配布の `allow` は空に保つ。** 承認削減を `allow` で行わない。
   個別の許可は [../.claude/rules/safety.md](../.claude/rules/safety.md) 5-1 の
   プロジェクト固有の事前検証方式で行う。
5. **常時読み込みルールの肥大化を止める。**
   詳細設計は必要時に読み込む資料（本書・スキル）へ分離する。

### 10-4. 編集経路の保護状況（検証結果）

公式仕様で確認した結果を記録する。

| 経路 | `ask` で止まるか | 備考 |
| :- | :- | :- |
| `Edit` / `Write` / `NotebookEdit` ツール | **止まる** | `Edit` ルールは「ファイルを編集する組み込みツール全般」に適用される |
| `.claude/**` への書き込み（全経路） | **止まる** | `.claude` は製品側の**保護パス**。`default` / `acceptEdits` では確認が出る |
| Bash のリダイレクト（`> file` / `>> file` / `2> file`） | **止まらない** | 検査対象は `Edit` の **`allow` と `deny`**、保護パス、作業ディレクトリ。**`ask` は検査されない** |
| `tee` の宛先 | **止まらない** | 同上（v2.1.269 以降で検査される） |
| スクリプトが内部で開くファイル | **止まらない** | permission ルールの適用外 |

**残る穴**：`CLAUDE.md` / `README.md` / `.gitignore` / `.gitattributes` は
`Edit` の `ask` で保護しているが、Bash のリダイレクト経路では止まらない。
これらは製品側の保護パスにも含まれていない
（保護ファイルの一覧には `.gitconfig` / `.gitmodules` / `.npmrc` などが
含まれるが、`.gitignore` と `.gitattributes` は含まれない）。

対応：
- 当面は**ルール文書上の禁止**として扱う
  （[../.claude/rules/safety.md](../.claude/rules/safety.md) 5-2）
- 恒久対応は `scope-file-guard` がリダイレクトと `tee` の宛先を検査すること（9.3）
- `deny` で塞ぐ案もあるが、`deny` にすると人間が Claude Code 経由で
  これらのファイルを編集できなくなるため採用しない

### 10-5. `defaultMode: acceptEdits` の評価と配布時の前提条件

**ai-workbench での使用**：適切と判断した。
このリポジトリはルール文書と設計書のみで構成され、アプリケーションコードを
持たない。保護が必要なファイルは次の 2 系統で守られている。

- `.claude/**` → 製品側の保護パス ＋ `Edit(.claude/**)` の `ask`
- `CLAUDE.md` / `README.md` / `.gitignore` / `.gitattributes` / `.github/**`
  → `Edit` の `ask`（リダイレクト経路の穴は 10-4 のとおり）

`docs/**` は `ask` を設けていないため `acceptEdits` で無確認に編集される。
設計書の更新は通常作業であり、許容する。

**他アプリへ配布する場合の前提条件**（配布前に確認する）

1. **対象アプリのワークスペースを信頼してよいか確認する。**
   `allow` ルールは trust 承認後に有効になる。
   trust ダイアログで付与される内容を人間が確認する。
2. **そのアプリで保護すべきファイルを洗い出し、`Edit` の `ask` または
   `deny` に追加する。**
   本基盤の既定（`.claude/**`、`.github/**`、`CLAUDE.md` 等）は
   アプリ固有の設定ファイル（スキーマ定義、インフラ定義、CI 設定、
   本番環境の設定）を網羅していない。
3. **`acceptEdits` が許容できる範囲かを判断する。**
   作業ディレクトリ内のすべてのファイルが無確認で編集される。
   機密性の高いファイルを含むリポジトリでは `default` に戻す。
4. 各開発者は `.claude/settings.local.json` の `defaultMode` で上書きできる。
   この手段を周知する。
5. **5-1 のプロジェクト固有の許可を設定する前に、スクリプトの中身を検証する。**

  **ソース上に literal で現れないよう文字列連結で組み立てている。**
  そうしないと、このリポジトリ自身の `secret-scan-precommit` が
  テストファイルの commit を拒否してしまう（実際に一度検出された。
  Hook が機能していることの裏付けでもある）。
- リポジトリ名のフィクスチャは `example-owner/example-repo` 等の中立な値を使い、
  実在の所有者名を再導入しない。

開発中に検出し修正した不具合：

1. `sed -i s/a/b/ <file>` で、sed のスクリプト部分（`s/a/b/`）を

   最初の非フラグ引数をスクリプトとして除外するよう修正。
2. `gh --repo owner/repo` の正規化で、すでに `owner/repo` 形式の値を
   URL として解析してしまい `repo` だけを取り出していた。
   `owner/repo` 形式をそのまま返すよう修正。
   併せて `--repo` の照合を**書き込み操作のみ**に限定した
   （読み取りを他リポジトリで行うことは害がないため）。

テスト設計の方針：

- **禁止固有名のリストをリポジトリ内に置かない。**
  置けばそれ自体が公開対象になってしまう。
  `AI_WORKBENCH_FORBIDDEN_NAMES`（JSON 配列のファイル）または
  `~/.claude/ai-workbench/forbidden-names.json` から読む。
  未提供の場合は汎用パターンのみで検査し、**検査が不完全であることを出力する。**
- **実行中のユーザー名もファイルに書かない。** `os.userInfo()` で実行時に取得し、
  ホームディレクトリ由来のパスが混入していないかを見る。
- 検査パターンは**自己テストを持つ**。既知の該当文字列を検出できることと、
  正常な記述を誤検出しないことの両方を確認する。
  これがないと「パターンが壊れていて何も検出しない」状態を PASS と誤認する。

開発中に検出し修正した不具合：

1. ブロックコメント内の `.claude/skills/*/SKILL.md` の `*/` が
   コメントを途中で閉じ、構文エラーになっていた。
2. 個人パス検査のパターンをファイルに literal で書いたため、
   **検査パターン自身が検査に引っかかった。** 実行時取得と文字コード組み立てに変更。
3. 同パターンが広すぎ、文書中のプレースホルダ `C:\Users\x` を誤検出した。
   3 文字以上かつ既知のプレースホルダを除外するよう修正。
4. `reviewer` / `security` / `tester` / `uiux-designer` の 4 件に
   「承認範囲を広げない」旨の記述が無かった。4 件に追記して再テスト。
