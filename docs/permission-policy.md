# permission 設定の方針

`.claude/settings.json` の `allow` / `ask` / `deny` をどう決めるかの方針と手順。

常時読み込みルール（[../.claude/rules/safety.md](../.claude/rules/safety.md) 第 5 節）
には要点のみを置き、判断基準と手順はこの文書に置いている。

関連：[guard-limitations.md](guard-limitations.md)（技術的ガードの限界）、
[ARCHITECTURE.md](ARCHITECTURE.md) 第 9〜11 節（Hooks と標準機能の調査）

## 1. 共通配布の `allow` に入れないもの

**現在 `allow` は空である。** 以下は、将来 `allow` へ追加する判断と、
5-2 のプロジェクト固有の許可を決めるときの基準として用いる。
全アプリへ配布する `allow` には、次を**入れない。**

| 入れないもの | 理由 |
| :- | :- |
| `npm run <script>` / `pnpm run` / `yarn run` 等 | **スクリプトの中身はプロジェクトごとに違う。** `build` という名前で本番デプロイが走る可能性があり、名前からは判断できない |
| `npm ci` / `npm install` / 依存インストール系 | パッケージの `preinstall` / `postinstall` が走る。**第三者のコードが無確認で実行される** |
| `pytest` / `go test` / `cargo test` 等のテスト実行 | プロジェクトのテストコードを実行する。`conftest.py` などが収集時に走る |
| `ruff format` 等のフォーマッタ | ファイルを一括で書き換える。Edit ツールを通らないため `Edit` ルールの保護が効かない |
| `git add` の無条件許可 | 範囲外のファイルや秘密情報を無確認でステージできる |
| `git stash` / `git stash pop` / `apply` | 作業ツリーを変更する。`pop` / `apply` は既存の変更を上書きしうる |
| 外部通信を伴うもの | 送信先と内容を事前に判断できない |

**承認回数を減らすために危険な操作を無条件で許可してはならない。**
これは公式仕様とも一致する。Claude Code は auto モードに入るとき、
**パッケージマネージャの run コマンドや広すぎる `allow` ルールを自動的に無効化する**
（`Bash(npm test)` のような狭いルールは残る）。
広い `allow` が安全でないことは、製品側の挙動としても示されている。

## 2. プロジェクト固有の許可（事前検証方式）

5-1 で共通配布から外した操作は、**各プロジェクトで事前に中身を検証してから
そのプロジェクトの設定で許可する。**

手順：

1. 対象スクリプト・コマンドの**中身を読む**
   （`package.json` の `scripts`、Makefile、タスクランナーの定義）
2. 次を確認する
   - 本番環境・共有環境に影響しないか
   - 外部へデータを送信しないか
   - 依存のインストールやコード取得を伴わないか
   - リポジトリ外のファイルを変更しないか
3. 問題がなければ、**狭いルール**として許可する
   （`Bash(npm run test)` のように対象を特定する。`npm run *` は使わない）
4. 許可先を選ぶ
   - **そのアプリの `.claude/settings.json`**：チーム全員に適用。
     コミットするため差分がレビューされる。trust 承認が必要
   - **各開発者の `.claude/settings.local.json`**：個人の環境のみ。
     Git 管理外で、未追跡なら trust 承認なしに適用される
5. スクリプトの中身を変更したら、**許可を見直す**
   （検証したときの内容と違うものが走る可能性がある）

`deny` は `settings.local.json` では緩和できない。
`deny` に入っている操作が業務上必要な場合は、共有ファイル側の見直しが必要であり、
人間に報告する。

## 3. `defaultMode` と編集経路の保護

`defaultMode` は `acceptEdits` としている。
許可範囲内のファイル編集と `mkdir` / `touch` / `cp` 等を確認なしで進められる。
`ask` と `deny` はモードに関わらず評価されるため、`.claude/**` や `.github/**` の
編集、Git 書き込み操作には引き続き確認が入る。
`bypassPermissions` は使わない（`disableBypassPermissionsMode` で無効化済）。

**`acceptEdits` の実機検証は未完了である。** 公式仕様に基づく設定であり、
実際に無確認で編集が進むか、保護対象で確認が出るかは確認していない
（[../../docs/ARCHITECTURE.md](ARCHITECTURE.md) 10-6）。

**編集経路ごとの保護状況（公式仕様で確認した結果）**

| 経路 | 保護 |
| :- | :- |
| `Edit` / `Write` / `NotebookEdit` ツール | `Edit` ルールが適用される（`Edit` ルールは「ファイルを編集する組み込みツール全般」に効く）。`ask` も有効 |
| `.claude/**` への書き込み | 加えて**保護パス**として製品側で保護される。`default` / `acceptEdits` では確認が出る |
| Bash のリダイレクト（`> file` / `>> file`） | **`Edit` の `allow` と `deny`、保護パス、作業ディレクトリのみが検査対象。`ask` は検査されない** |
| `tee` の宛先 | 同上 |
| スクリプトが内部で開くファイル（Python / Node のコード） | **permission ルールの適用外** |

**したがって次の穴がある。**
`CLAUDE.md` / `README.md` / `.gitignore` / `.gitattributes` は `Edit` の `ask` で
保護しているが、**Bash のリダイレクトで書き換える経路は `ask` では止まらない。**
これらは製品側の保護パスにも含まれていない。
`.claude/**` は保護パスに含まれるため、この経路でも保護される。

この穴を埋めるのは Hook である（`scope-file-guard` がリダイレクトと `tee` の
宛先を検査する）。実装までは、**ルール文書上の禁止として扱う。**
エージェントは設定ファイル・ルール文書をリダイレクトで書き換えてはならない。
変更が必要なら `Edit` ツールを使い、確認を受ける。

**読み取り専用の操作を `deny` に入れない。**
`deny` は `allow` で例外を作れないため、`deny` に入れた操作は承認による回復手段が失われ、
各開発者が `settings.local.json` で緩和することもできなくなる。
調査・診断が必要な操作は `ask` に置き、承認で通す。
